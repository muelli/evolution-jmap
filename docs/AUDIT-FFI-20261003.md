## 3. Audited and clean

### 3.1 `jmap-backend-collection/tests/live_server_removal.rs`'s new
    `unsafe impl Collection for Collection`

New real-Stalwart coverage for `fan_out`'s removal half (`97f895f0`) needed
its own test-local mock, following `tests/fan_out.rs`'s existing pattern of
implementing the crate's `unsafe trait Collection` for a test struct. The
trait's safety contract (`new_child`/`existing_children`/`publish` must hand
out valid `ESource` pointers each carrying their own reference) is upheld the
same way the pre-existing `tests/live_server.rs`/`tests/fan_out.rs` impls
already do: `new_child` takes a reference via `e_source_new_with_uid` and
hands out a second one via `Source::dup` (an internal `g_object_ref`
wrapper), `seed_existing` takes its own ref with an explicit `g_object_ref`
safety-commented call, `existing_children` hands out fresh refs via the same
`dup`. No behaviour this impl's three call sites rely on differs from the
already-audited originals it was copied from.

### 3.2 `jmap-config`'s `credential-store-id`/`credential-name` cfg dispatch
    (item 73, `account.rs`/`build.rs`; `jmap-backend-collection`'s
    `child_added.rs`/`mail_child.rs`)

The property-name constant each file writes (`set_credential_id` in
`account.rs`, `CREDENTIAL_PROPERTY` in `child_added.rs`, reused by
`mail_child.rs`) is `#[cfg]`-dispatched on the same `eds_credential_store_id`
marker, itself derived (not guessed) from whether the installed EDS's
generated bindings declare `e_source_authentication_set_credential_store_id`.
Since no header anywhere this repository builds against yet declares eds#663
(confirmed again this session: Fedora 44's `evolution-data-server-devel` is
still 3.60.2, upstream's own tags still top out at 3.62.0, and the eds#663
commit sits strictly after 3.62.0 in `3.62.0..master`, the same finding item
77's 2026-10-01 feasibility check already recorded), every build today still
takes the `credential-name` branch unconditionally; the new branch compiles
(both `#[cfg]` arms are checked by `cargo clippy --all-targets`) but has never
actually linked against a real `credential-store-id` setter. This is the same
acknowledged gap item 73 itself names, not a new one. The getter/setter pair
written is a plain `*const c_char`/NULL dispatch identical in shape to the
pre-existing `credential-name` call it replaces; no new ownership question
arises since neither setter takes ownership of the string (both are
documented EDS property setters that copy).

### 3.3 `jmap-functional`'s `spawn_loopback_proxy`/`relay`

New test-harness-only code (`jmap-functional` is a dev-dependency, gated out
of `default-members`, never shipped). Binds only to `127.0.0.1:0`: satisfies
the same plaintext-stays-loopback rule `jmap-backend-core::rebase`'s module
doc states, rather than working around it: the backend's own plaintext
traffic genuinely never leaves loopback, and the proxy's onward hop to the
real server is the same hop every other live-server test in this workspace
already makes directly from its own test process. `relay` spawns one thread
per direction per connection with no cap, which would be a DoS surface in
product code but is not one here: nothing but this repository's own CI and a
developer's own local run ever connects to this port, and it is invoked only
from `#[ignore]`d tests that need a human or CI job to opt in. Both
directions close cleanly on either side disconnecting (`try_clone`/
`std::io::copy` returning, no explicit shutdown needed since dropping the
`TcpStream` on scope exit closes the socket).

### 3.4 `jmap-backend-{book,cal,collection}-module`'s new `build.rs` (item 80
    stage 1 RUNPATH fix)

All three are the same fix, applied to the two additional cdylib crates
whose vfuncs' C callers also load the linked `evo-sys`/`jmap-config`
transitive dependency on Evolution's own private libdir, mirroring the
already-shipped `jmap-config-module/build.rs` this session confirmed is
unchanged (not a new finding, carried forward from before this delta). The
one file-scoped question worth checking directly rather than trusting the
commit message, whether `-Wl,-rpath,{dir}` can inject anything hostile via
`DEP_EVOLUTION_SHELL_LIBDIRS`, is closed the same way it was for the
original: that variable is Cargo's own build-script-to-build-script channel,
populated entirely from `evo-sys`'s own `pkg-config` query against
`evolution-shell-3.0`, never from any JMAP-server- or network-derived input,
so it is not part of this threat model's adversarial input surface.

### 3.5 `jmap-collection-sync`'s `shown_name` fix

`match name.trim() { "" => ..., name => name.to_owned() }`'s second arm
shadowed the outer `name: &str` parameter with the *trimmed* slice the match
scrutinee produced, so a non-empty, padding-only-different name silently lost
its leading/trailing whitespace on its way into Evolution's sidebar. A
correctness bug, not a safety one (no FFI, no unsafe, pure string handling),
fixed by switching to an explicit `if name.trim().is_empty()` that returns
the *original* `name.to_owned()` on the non-empty branch. `tests/create.rs`
covers the padded-name case directly.

### 3.6 `jmap-client`'s `maxObjectsInGet` chunking, `CalendarEventNotification`
    capability routing, and `ParticipantIdentity/get`'s response shape

All three are pure-Rust protocol-layer changes with no FFI surface.
`Client::get_email`'s new `max_objects` clamp
(`.and_then(|limit| usize::try_from(limit).ok()).filter(|&limit| limit > 0)`)
handles a server-advertised negative or zero `maxObjectsInGet` by falling
back to the existing `ids_that_fit` byte-budget split rather than panicking
or chunking to zero, which would loop forever; `take.min(max_objects)` is the
only new arithmetic and cannot underflow (`take` and `max_objects` are both
plain `usize`, `min` never produces a value outside either input's range).
`changes.rs`'s capability match gains one more `CalendarEventNotification =>
CAPABILITY_CALENDARS` arm, pure data, no default-arm change. The new
`ParticipantIdentityGetResponse` (`#[serde(default)] list: Vec<...>`)
tolerates a server that omits `list` entirely on an empty result instead of
erroring, strictly more permissive input handling than the previous direct
`GetResponse<ParticipantIdentity>` deserialize, not less.

### 3.7 New/changed C test clients (`cal-live-client.c`; small changes to
    `book-client.c`, `collection-client.c`, `mail-client.c`)

`cal-live-client.c` is new but mirrors `cal-client.c`'s existing
`first_vevent`/`joined_values`/`first_alarm_trigger` helpers line-for-line in
ownership shape (every `i_cal_component_get_first_component`/
`get_first_property`/`get_next_property` result is paired with exactly one
`g_object_unref`, including on the early-return paths). `book-client.c`'s and
`cal-live-client.c`'s new password-seeding block
(`e_source_store_password_sync`, gated on `JMAP_FUNCTIONAL_STORE_PASSWORD`
being set) and `collection-client.c`'s added
`e_source_invoke_authenticate_sync` retry are both read-environment-variable,
test-harness-only code with no product-facing effect; the password is a
throwaway Stalwart test account's, read from an env var the harness itself
sets, never from server- or network-derived input. `mail-client.c`'s
`folder_dup_uids`/`folder_free_uids` compat shim correctly pairs
`camel_folder_dup_uids` (owned, 3.60+) with `g_ptr_array_unref` and
`camel_folder_get_uids` (borrowed, pre-3.60) with `camel_folder_free_uids`,
matching `eds-sys`'s own compat layer's pairing for the identical two names
(this client links no crate from this repository, so the pairing is
necessarily duplicated here as plain C, per the file's own comment).
