## 1. Findings

### F28 (fixed): `transport-live-client.c` leaked the transport `CamelService`

**Severity: info/low** (test-harness-only, non-shipped, single-process CLI
that exits immediately after use — no production impact, no security
impact. Recorded because it is a real, confirmed ownership bug and the
standing hunt list calls for GObject refcount/ownership findings
regardless of where they land).

`main()` calls `camel_session_add_service(session, transport_uid, protocol,
CAMEL_PROVIDER_TRANSPORT, &error)` to get the transport `CamelService` it
sends through. Per `Camel-1.2.gir` (`camel-session.c:875`, confirmed against
the installed 3.52.3 GIR, `source-position` `src/camel/camel-session.c`):

> The returned #CamelService is referenced for thread-safety and must be
> unreferenced with g_object_unref() when finished with it.

`service` is used through `camel_service_connect_sync`,
`camel_transport_send_to_sync` and `camel_service_disconnect_sync`, then
never unreferenced on any path: not on the `connect`/`send`/`disconnect`
failure paths (each does `status = fail(...); goto out;` with no
`g_object_unref(service)`), and not on the success path either (the
function moves straight on to reopening the sender/recipient stores, then
to the common `out:` cleanup block, which cleans up `session`,
`recipient_account`, `transport_source`, `identity`, `account` and
`registry` but never named `service`).

This is a straightforward inconsistency against the file's own sibling
function, `open_account_store` (same file), which calls the same
`camel_session_add_service` and correctly either unrefs on its own failure
path or hands the reference off by returning `CAMEL_STORE(service)` to a
caller that later unrefs the store. `transport-live-client.c`'s `main()`
does neither for the transport service.

**Fix** (this branch): initialize `CamelService *service = NULL;` at
declaration and add `g_clear_object(&service);` to the common `out:`
cleanup block, the same centralized-cleanup treatment the file already
gives `session`/`registry`/the four `ESource` refs, rather than scattering
a new `g_object_unref(service)` across every one of the five paths that can
reach `out:` after `add_service` succeeds (which is exactly the kind of
scatter that let this leak happen in the first place).

**Verification.** No unit-test framework exists for this file (like every
client in this directory, it is an oracle a Rust test drives, not a
predicate of its own — see the file's own header), and reproducing the leak
live needs the full functional harness (real D-Bus session, EDS factories,
a throwaway Stalwart account), which `ci/checks.sh` does not build
(`ENABLE_FUNCTIONAL_TESTS` is off in the default gate). Verified instead by:
isolated compile, `gcc -c tests/functional/transport-live-client.c -Wall
-Wextra` against the installed camel-1.2/libedataserver-1.2 headers, zero
warnings before or after the fix; and an isolated link against the same
libraries, exit 0. The fix is two lines, mechanically checked against the
GIR's own transfer-ownership annotation for every other call site in the
same file that already follows it correctly (`open_account_store`'s
`g_object_unref(session)`/`g_object_unref(service)` pair on its own error
path, unchanged by this commit).

## 3. Audited and clean

### 3.1 `mail-live-client.c` (new, 1098 lines)

Read in full. Every `CamelFolderInfo`/`CamelMessageInfo`/`GPtrArray`/
`CamelMimeMessage` obtained is paired with exactly one free/unref on every
path checked, including the error paths inside `report_reopened`,
`report_reopened_filed` and the three transfer-phase branches in `main`
(each explicit `g_object_unref(scratch)`/`g_free(appended_uid)` before
`return fail(...)` was checked against where `scratch`/`appended_uid` was
acquired). `open_store`'s `service`/`session` pair is the one this file gets
right: on failure it unrefs both; on success it folds `service` into the
`CamelStore *` it returns, which every caller later unrefs — the same shape
`transport-live-client.c`'s `open_account_store` uses correctly and its
`main()` (F28) did not.

The `folder_dup_uids`/`folder_free_uids` compat pair matches `eds-sys`'s own
version-gated pairing for the identical two Camel symbols (3.60+:
`camel_folder_dup_uids` plus `g_ptr_array_unref`; earlier:
`camel_folder_get_uids` plus `camel_folder_free_uids`), the same shape the
2026-10-03 report already found clean in `mail-client.c`'s copy.

The end-of-`main` comment explaining why `g_main_context_iteration(NULL,
FALSE)` is drained before teardown (a real, previously-hit hang/crash this
session's own delivery notes describe: `ESourceRegistry`'s dispose
dispatching a pending `folder_changed` closure into a `CamelStore`
finalizer that is already holding the lock the closure wants) was checked
against the mechanism it describes: `g_signal_connect_object`/ordinary
GObject closures on the default `GMainContext` are exactly what
`camel_folder_changed()` posts through, and nothing in this file runs its
own main loop, so the drain is load-bearing, not decorative.

Exit-path leaks of `inbox`/`store`/`session`/`account_source`/`registry`
reached via `return fail(...)` before the end of `main` (for example after
`trash`/`junk` folder-lookup failure) are real but match this file's own
documented purpose and every sibling client's own convention: a short-lived
CLI oracle that exits non-zero on the first failure, process exit reclaims
everything, and no later call in the same process depends on the freed
state. Not a new pattern and not flagged, consistent with how the
2026-10-03 report treated the same shape in `cal-live-client.c`.

### 3.2 `transport-live-client.c` (new, 740 lines) beyond F28

Everything else in this file was checked the same way: `from`/`recipients`/
`message` are each unreffed exactly once right after the send call on both
the failure and success paths; `sent_folder`/`drafts_folder`/
`recipient_inbox`/`sender_store`/`recipient_store`/`sender_session`/
`recipient_session` are each unreffed on every path that acquires them
(checked path by path, the same density of `goto out`/explicit-unref pairs
`mail-live-client.c` uses); `delivered_uid`/`staged_uid`/`sent_copy_uid`/
`recheck` (`gchar *`, from `find_by_subject`/`g_strdup`) are freed exactly
once each, with `recheck` reused for both the sender and recipient cleanup
checks and freed after each use rather than carried over. The
`test_session_get_password` vfunc answers the currently-connecting
account's password via the `current_password` static, set immediately
before each of the two `camel_service_connect_sync`/`add_service` calls
(transport, then sender reopen, then recipient reopen) — read order
confirmed by hand against the three assignment sites, no stale value from
an earlier account can leak into a later one since each is set
synchronously on the same thread immediately before the call that consumes
it.

### 3.3 Small additions to `cal-changes-client.c`, `cal-free-busy-client.c`,
    `config-lookup-client.c`

All three are small, env-gated, test-harness-only additions with no new
ownership surface:

- The password-seed blocks (`cal-changes-client.c`, `cal-free-busy-client.c`)
  are a straight copy of `cal-live-client.c`'s own already-audited
  (2026-10-03) `e_source_store_password_sync` call, gated on
  `JMAP_FUNCTIONAL_STORE_PASSWORD` being set; no new object is created, no
  new free is owed.
- `cal-changes-client.c`'s `functional_report_connection_status(source, 10)`
  call is to an existing, unchanged helper (`connection-status.h`/`.c`, not
  part of this delta — confirmed by `git diff 49440f05..HEAD --
  tests/functional/connection-status.*` being empty); only the call site is
  new.
- `config-lookup-client.c`'s `worker_finished_cb` is the one new callback
  here. It takes no reference on anything it is handed (`EConfigLookup`,
  `EConfigLookupWorker`, `ENamedParameters` are all borrowed per the
  signal's own signature) and manages exactly one owned value,
  `state->worker_error`: `g_clear_error` before every `g_error_copy`
  assignment (so a second `"worker-finished"` emission in one run cannot
  leak the first error), and the call site after `e_config_lookup_run`
  prints the message and calls `g_clear_error` again before `state` goes
  out of scope. Checked that no other path through `main` can return before
  that final `g_clear_error` runs: every `return`/`goto`-equivalent in this
  function between the signal connection and that point is a `return
  fail(...)` or `return 1`, which (same as 3.1 above) is a process exit, not
  a call that leaves a dangling heap-owned `GError*` for a later line to
  touch.
