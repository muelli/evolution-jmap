## 1. Findings

### F32 (INFO, test infrastructure only): `jmap_tracing_capture::capture` loses events across a nested call on the same thread

`rust/crates/jmap-tracing-capture/src/lib.rs:120-128`. `capture` always resets
the calling thread's `SCOPE` to `None` when it returns, rather than restoring
whatever `SCOPE` held before it ran:

```rust
pub fn capture<T>(run: impl FnOnce() -> T) -> (T, Captured) {
    ensure_installed();
    let sink = Arc::new(Mutex::new(Vec::new()));
    SCOPE.with(|scope| *scope.borrow_mut() = Some(sink.clone()));
    let result = run();
    SCOPE.with(|scope| *scope.borrow_mut() = None);
    let captured = std::mem::take(&mut *sink.lock().unwrap());
    (result, captured)
}
```

If a test's `run` closure itself calls `capture` again on the same thread
(directly, or through a helper it calls), the inner call's own `None` reset
on return clears the outer call's scope too. Any event the outer closure
traces *after* the inner `capture` returns is silently dropped: `SCOPE` reads
`None` at that point, so `Router::event`'s `if let Some(sink) = ...` guard
skips it, exactly like an uninstrumented thread. This is not the race item
103 exists to fix (that one is cross-thread, at first-callsite-touch time);
it is a same-thread, same-process ordering bug in the new helper itself.

`rust/crates/jmap-tracing-capture/tests/isolation.rs`, the stress-loop proof
item 103's own in-progress claim is built around, only exercises concurrent
captures on independent threads (`concurrent_captures_never_see_another_
thread_s_event`, `capturing_is_unaffected_by_concurrent_non_capturing_
calls`); neither test nests a `capture` call inside another on the same
thread, so this gap is not covered by the proof that lock is for. Checked
the 13 migrated call sites by hand (`grep -rln jmap_tracing_capture::capture
rust/crates`): none of them currently nests a call, so this is not an active
bug in anything shipped or tested today, only a landmine for a future test
that does, in a crate explicitly meant to make that class of mistake harder,
not easier.

**Not fixed this round.** `jmap-tracing-capture/src/lib.rs` and its
`tests/` are the exact surface item 103's stress-loop-proof claim (harness
commit `5624aa3`, 2026-10-14 23:12 UTC) is still locked on as of this audit
(about 22h13m old, under the 24h deadlock threshold); every comment-sweep
round since has deferred touching this crate for the same reason. The fix
itself is small (save the previous `SCOPE` value on entry, restore it on
exit, instead of unconditionally clearing to `None`), with an obvious
red-first test (nest a `capture` call and assert the outer buffer still has
the event traced after the inner one returns). Left for whoever next holds
or inherits that lock, alongside the stress-loop proof itself.

### `jmap-backend-core/src/source.rs`: trailing-dot host normalization (item 101a)

Commit `65594e00`. `connect_target` now does
`host.trim_end_matches('.')` before computing the authority, matching
`resolver.rs:62`'s existing identical handling for SRV answers byte for
byte. A fully-qualified name's single trailing dot (RFC 1035 §3.1) and its
relative form are the same DNS entry; left unstripped, a URL built from it
becomes a host string Fastmail's own redirect target does not match,
which is what dropped the bearer token in the operator's original report. No
unsafe code in the function; `authority()` (the next call) already rejects
an empty host with `SourceError::MissingHost`-shaped errors rather than
panicking, checked directly, so the one edge case worth checking (`host` is
just `"."`, trimming to an empty string) fails closed rather than panicking.
CLEAN.

### `jmap-backend-core/src/connect.rs`: `ConnectError::auth_result` maps a withheld-credentials redirect to `UNKNOWN`, not `ERROR` (item 101, final root cause)

Commit `ea7e61c3`, overturning this same item's own prior-round `ERROR`
mapping once live-EDS testing showed `ensure_connected_sync` escalates to
interactive consent for every value except `UNKNOWN`. Pure match-arm logic
in safe Rust; the one `unsafe fn` nearby, `write_auth_result`
(`connect.rs:592-601`), is a generic "write through this pointer if it is
not NULL" primitive untouched by this change and indifferent to which
`ESourceAuthenticationResult` value it is asked to write. New test
`a_redirect_that_withheld_credentials_is_unknown_not_an_escalation` pins the
mapping directly. CLEAN.

### `jmap-ui/src/link.rs`: a dedicated account-editor message for the withheld-credentials case (item 101b)

Commit `57b9ea91`. `describe()` gained one match arm naming both hosts
involved, ahead of the catch-all that would otherwise print the error's raw
`Display` text (a `401` message, misleading for a failure a password cannot
fix). Two new unit tests pin it. No FFI surface in this file. CLEAN.

### `jmap-client/src/url.rs`: `resolve_redirect` no longer panics on a malformed `current_url` (hostile-input fix)

Commit `621b075c`, found by this crate's own `proptest` suite (regression
pinned in `proptest-regressions/url.txt`). `current_url` is built by
following the untrusted server's own redirect chain, so it is not guaranteed
well-formed on every hop; a `?` appearing before the `://` made
`url_without_query` shorter than `path_start`, and the old code indexed
`url_without_query[path_start..]` directly, panicking (a DoS an untrusted
server could trigger simply by redirecting through a crafted `Location`).
The fix changes the index to `.get(path_start..).and_then(|rest|
rest.rfind('/'))`, which reads "no path region there" the same as "no slash
found" instead of panicking. Traced the two downstream uses of the resulting
`Option` (`&current_url[..=idx]` and the `None` fallback
`format!("{current_url}/{location}")`): `idx`, when `Some`, is always
computed from an offset into `url_without_query`, which is byte-for-byte a
prefix of `current_url`, so the slice stays in-bounds on a valid UTF-8
boundary either way. CLEAN, and an improvement: this closes a real
untrusted-input panic that predates this delta's base.

### `tests/functional/redirect-credentials-withheld-client.c`: new hand-written EDS acceptance-test client

Commits `452fb3ce`/`d7b776a6`/`ea7e61c3`. 205 new lines of C driving a real
`EBookMetaBackend` connect through a front door that 302s to a different
origin and 401s the credentials-stripped follow-up request. Read in full as
new FFI-adjacent surface even though it is test-only, since a bug here could
misreport a real product regression as green. Reference counting checked
call by call: `e_source_registry_new_sync` and
`e_source_registry_ref_source` each return an owned reference, both
`g_object_unref`'d exactly once on every exit path including the early
`return 1` after a failed first connect; `e_book_client_connect_sync`'s
`client` likewise. No double-free, no leak on any path, including the error
paths `fail()` handles. The `credentials-required` signal handler is
connected once and never explicitly disconnected, but the owning `source` is
unref'd at the very end with no further signal traffic possible after, so
this is not a dangling-callback risk. Matches the structure of the existing
`book-stale-token-client.c` this file's own comments cite. CLEAN.

### `jmap-tracing-capture/src/lib.rs` (new crate): shared global-subscriber capture helper (item 103)

~130 lines, no unsafe. Read in full given it introduces process-global
mutable state (a `OnceLock`-guarded `tracing::subscriber::set_global_
default` call) deliberately designed to be touched from many concurrently
running test threads. The cross-thread isolation property it exists to
provide is sound: `Router::event` only ever reads the *calling* thread's own
`thread_local!` `SCOPE`, so two threads capturing concurrently cannot
observe each other's events regardless of which callsite's `Interest` gets
resolved first process-wide, which is exactly the race item 103 was opened
to kill. One gap found, F32 above (same-thread nesting, not cross-thread
racing). `ensure_installed`'s `.expect()` on a failed `set_global_default`
is a deliberate test-binary-only panic (a second, different global
subscriber already installed by something else in the same binary), not a
reachable path in the shipped product: this crate is test-only tooling, not
linked into any product crate's non-test build.
