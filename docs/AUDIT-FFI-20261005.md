## 1. Findings

### F29 (fixed): unverified principal-identity resolution could accept a decoy

**Severity: low** (no production caller yet — `jmap-client::principals`'s new
`current_user_principal`/`current_user_principal_id`/`principal_get` fallback
is not called from any backend crate in this delta or before it, confirmed by
`grep -rn` across `jmap-backend-book`, `jmap-backend-cal`,
`jmap-backend-collection` finding nothing. Recorded and fixed now, before a
caller lands, because the defect is real and the whole point of this
function is to resolve identity from untrusted server data).

**Where** `rust/crates/jmap-client/src/principals.rs`, `resolve_owner_principal`
and its two call sites (`current_user_principal`, `principal_get`), added
this delta (`fc38e908`, "Tolerate Stalwart account ID as
currentUserPrincipalId, resolve true owner principal", Batch 25 finding 18).

**Why it is exploitable.** `resolve_owner_principal` is the fallback used
when the session's advertised `currentUserPrincipalId` is missing or (real
Stalwart's own non-conformance, finding 18) is the account id rather than a
principal id. It asks the server, via `Principal/query`, for principals whose
name or email contains the session's own `username` — RFC 9670 §2.4.1
defines both the `text` and `email` filters as substring containment, not
exact match — and then, before this fix, accepted **whichever principal id
the query returned first**, with no check that it was actually the right
one:

```rust
if let Ok(ids) = self.principal_query(account_id, filter) {
    for candidate_id in ids {
        if let Some(principal) = self.fetch_principal(account_id, &candidate_id) {
            return Ok(Some(principal));
        }
    }
}
```

`fetch_principal` succeeds for any id the server answers with a `Principal`
object for, so this loop's only real effect was "return the server's first
answer." A server (hostile, or merely one with more than one principal
sharing a substring with the account's own login name — RFC 9670 §2 itself
anticipates "a user may have access to a large number of Principals" in a
shared environment) can return its principals in any order, so whichever one
happened to sort first would be treated as the account owner, with no
further check. The final fallback (full `principals(account_id)` listing)
was no better: it accepted any principal with `is_personal == Some(true)`
before even checking the username, and `Principal` has no such property —
RFC 9670 §2 lists exactly `id`/`type`/`name`/`description`/`email`/
`timeZone`/`capabilities`/`accounts`, no `isPersonal`, and neither the mock
server nor (per `STALWART-RFC-FINDINGS.md`) real Stalwart has ever been
observed to set one, so that clause could never actually fire — dead code
that reads as a verified check when it is not.

Nothing in this delta calls these functions for a real decision yet, so there
is no live path from this to a wrong action today. But the function exists
specifically to answer "which principal is me" from server-controlled data,
and a future caller (scheduling, ACL/sharing UI) reading that answer at face
value would silently act as, or disclose availability for, the wrong
principal.

**Evidence** `rust/crates/jmap-client/tests/principals.rs`,
`current_user_principal_does_not_accept_an_unverified_decoy_candidate`: seeds
an account named `"alice"` with two principals, a decoy
(`alice.decoy@example.com`, seeded first so a first-candidate-wins bug picks
it) and the real owner (`alice@example.com`, seeded second). Confirmed red
before the fix (stashed the source change, kept the test): resolves to the
decoy's id. `STALWART-RFC-FINDINGS.md` finding 18's own tests
(`stalwart_tolerances.rs`) continue to pass unmodified; they only ever seed
one candidate, so they could not have caught this.

**Fix** (this branch, one commit): `resolve_owner_principal`'s two
`Principal/query` fallbacks now run every returned candidate through a new
`principal_identifies_username` check before accepting it (exact email
match, or — when `username` carries no `@` and is plausibly a bare login
name — the local part of the candidate's email, or an exact name match),
via a new `find_verified_principal` helper shared by both filter attempts.
The final full-listing fallback uses the same predicate and drops the dead
`is_personal` clause rather than reinstating it. No behaviour change for the
single-candidate case every existing test (including finding 18's own) only
ever exercises: `an exact or local-part match still accepts the one real
candidate`, confirmed by the full existing `principals.rs`/
`stalwart_tolerances.rs` suites passing unmodified.

**Verification.** `cargo test -p evolution-jmap-client` (all suites,
including `principals.rs` and `stalwart_tolerances.rs`) green; `cargo clippy
--all-targets --locked -- -D warnings` clean; `cargo fmt --check` clean;
full `ci/checks.sh` green on this branch (section 4).

## 3. Audited and clean

### 3.1 `jmap-mail/src/cache.rs`'s new atomic-write arm (item 87, `cc2a4c44`)

The only new `unsafe` surface this delta adds. Read against the real
upstream contract, not assumed symmetric with the pre-3.62 arm: fetched
`camel-data-cache.h`/`.c` directly from GNOME's `master` branch (anonymous
HTTPS, no clone needed) rather than trusting the delivering session's own
description of it.

Confirmed from the header's doc comments (`camel-data-cache.c:479-648`):
`camel_data_cache_add_atomic` returns a `(transfer full)` `GIOStream*` that
must be passed to exactly one of `commit_atomic`/`discard_atomic` — "Do not
call g_object_unref() on it directly" is the function's own doc text — both
of which take `@stream: (transfer full)` and close/unref it themselves.
`commit_atomic` additionally returns its own `(transfer full)` `GIOStream*`
on success (a fresh handle on the now-renamed file) or `NULL` on failure, and
on failure it has already cleaned up the temporary file and bag reservation
itself, so the doc text is explicit that the caller "does not need to call
`camel_data_cache_discard_atomic()`" in that case.

The Rust side matches this exactly: the `Owned<GIOStream>` wrapper around
`add_atomic`'s return is consumed via `.into_raw()` exactly once on every
path (the write-failure branch hands it to `discard_atomic`, the
write-success branch hands it to `commit_atomic`), so there is no double
free and no path that leaves it unreleased; `commit_atomic`'s own return
value is wrapped in `Owned::from_raw(..).is_some()` as a throwaway
success/failure check, which correctly drops (unrefs) the fresh stream it
hands back since nothing downstream needs it open. No `g_object_unref` is
ever called directly on any of these streams, matching the doc's own
warning against doing so.

### 3.2 `jmap-mail/src/connect.rs`'s `StoreError::Unauthenticated` (`d5d3ee96`)

Safe Rust, no FFI. `client.is_anonymous()` is checked once, immediately after
`source::connect` and before any account is resolved, so a session that is
merely missing the mail capability (a real, authenticated session) cannot be
misclassified — confirmed by reading the one call site and its guard
ordering, and by the existing no-mail-capability test in the same file's
suite continuing to pass unchanged.

### 3.3 `jmap-client`'s other new surface: `is_anonymous`, `is_unrecognized_changes_state`, `mailbox_create`'s omitted-property fallback, `calendar_event_notification_destroy`'s dropped-id tolerance

All safe Rust, all narrowly scoped to tolerating a specific, cited Stalwart
deviation (`STALWART-RFC-FINDINGS.md` findings 12/16/17/20), each with its
own pinned mock-transport regression test in `stalwart_tolerances.rs` using
the exact wire JSON a real server was observed to send. `mailbox_create`'s
fallback only ever substitutes the caller's own just-sent request data for a
property the server omitted (RFC 8620 §5.3 permits omitting unchanged
properties) — it never trusts a server-asserted value over what was asked
for, so there is no injection surface here distinct from what `Mailbox/set`
already accepts. `is_unrecognized_changes_state`'s description-text match is
a heuristic by its own admission (doc comment); its only effect on a false
positive is an unnecessary full resync, not a wrong one, and is exercised by
both a positive and two negative unit tests.

### 3.4 `jmap-mail-sync/src/lib.rs`'s fold-in of the new predicate (item 85)

`folder_tree_since`/`refresh_folder`'s existing `is_cannot_calculate_changes`
branches gained an `|| error.is_unrecognized_changes_state()` arm each,
reusing the existing rebuild/relist fallback rather than adding a new one.
Same shape already audited for the RFC-defined condition in earlier reports;
nothing new to the control flow itself.

### 3.5 `jmap-mock` additions (`dispatch.rs`, `server.rs`, `setops.rs`, `state.rs`)

Test-harness-only, not shipped. `store_changes` gained one new `bool`
