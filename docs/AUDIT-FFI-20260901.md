2026-09-01, against EDS 3.52.3 on this runner. Branch
`audit/reaudit-20260901`, forked off master at `962141b`.

Two sessions so far, and they cover different halves. **Sessions 1 (§1 to §5)
is part 1**, what the last audit lost: the re-verification of the prior
findings, and the three fixes that had to be re-landed because the 2026-08-28

**Base commit diffed against: `962141b`'s merge base with
`audit/reaudit-20260828`, which is `3858139`** ("item 23: refresh the access
token and retry once on a 401 in mail's transport"). That is not the base the
previous report names, and the discrepancy is itself this session's second
finding: see P2 below. The delta from `3858139` to `962141b` is **193
commits, 188 files and 34 612 insertions** in `rust/`.

This session covers **part of the recurring protocol's step (1)**, re-verifying
that every prior finding's recorded disposition still holds against today's

Splitting it that way was not the plan: step (1) was expected to be a
morning's confirmation, and instead it found that the previous audit's fixes

re-land properly. F16 to F19 and F1 to F4 were re-verified; F5 to F15 were

Threat model unchanged from every prior session: **the JMAP server is not
trusted**, this code runs inside processes serving the user's other accounts,
and an OAuth provider is adversarial input too. The consequence of getting the
`EOAuth2Service` vtable wrong is not a crash but a silent authentication
failure the operator sees as a consent window that will not stop reappearing.

### P1. The 2026-08-28 re-audit was never merged, so none of its fixes shipped

**High, and the reason every other line in this table needed rewriting.**

`git merge-base --is-ancestor` answers plainly:

    audit/ffi                    merged-into-master: NO   (content landed separately)
    audit/reaudit-20260814       merged-into-master: YES
    audit/reaudit-20260828       merged-into-master: NO

None of `audit/reaudit-20260828`'s seven commits were cherry-picked onto
master either, and its report file does not exist there: master's `docs/`
carries `AUDIT-FFI-20260810.md` and nothing newer. So for four days the
project believed F16, F17 and F19 were fixed, believed the regression tests

All three bugs were verified live on master before anything was changed:

* **F16.** `oauth2_service.rs:177-190` still saved EDS's three `prepare_*`
  defaults into `OnceLock`s and `:219`, `:325`, `:366` still called them. The
  module header at `:30-49` meanwhile already described the correct semantics,
  so the file contradicted itself: the prose said the default "runs first,
  always", the code chained to it as though it did not.
* **F17.** `:243-259` still added `code_challenge` unconditionally while
  stashing the verifier only for a source with a uid, and `:346-350` still
  reported a missing verifier at `debug!`.
* **F19.** `jmap-mail/src/oauth2.rs`'s failure branch still had no trace of
  any kind.

**Fixed here**, as three commits on this branch, each with its red test
confirmed failing against `962141b` first. They are ports rather than
cherry-picks: master has moved 193 commits since that branch forked, and both
files changed underneath it. Two adaptations were needed and are worth naming,
because they are the kind of thing a blind merge would have got wrong:

1. `oauth2_service.rs` grew `scope`, RFC 8707 `resource` and RFC 7636 PKCE
   after the audit branch forked. The F16 fix had to be re-derived over that
   code, not applied to it: the three overrides now add five parameters
   between them where the branch's version added two.
2. F19's `a_dead_dbus_peer_is_traced_as_a_secret_store_failure` asserted
   `reason=secret_store_failure`. Master's `SilentRefreshFailureReason` has
   since gained a distinct `ServiceGone` member, and `is_service_gone`
   correctly classifies a dead D-Bus peer as that, so the test asserts
   `service_gone` and is renamed to match. This is the current code answering
   correctly, not a weakened assertion: both reasons agree on
   `escalates_to_consent=false`, which is the half that decides what the user
   sees.

**The verification each fix rests on was re-run here, not inherited.** EDS's
own `e-oauth2-service.c` (3.52.3, on this runner at
`/var/tmp/evolution-data-server-3.52.3`) was re-read rather than trusted from
the previous report, and it says what that report said it says:

    320: iface->prepare_authentication_uri_query = eos_default_prepare_authentication_uri_query;
    648: eos_default_prepare_authentication_uri_query (service, source, uri_query);
    654: if (iface->prepare_authentication_uri_query != eos_default_prepare_authentication_uri_query)
    655:         iface->prepare_authentication_uri_query (service, source, uri_query);

and identically at `:822`/`:828` for the code grant and `:895`/`:901` for the
refresh grant. The default is installed into the slot, run unconditionally by
the wrapper, and the slot consulted only afterwards and only when it differs.
A filled slot that also invokes the saved default runs it twice.

**This finding is not closed by those three commits.** The bug was the merge,
not the code, and this branch is in exactly the position the last one was: its
fixes reach nobody until someone merges it. Whatever caused a completed,
green, `AUDIT COMPLETE` branch to be left behind will do so again.

### F18. The PKCE verifier map holds a secret indefinitely and does not zeroize

Info, unchanged and still open. `pkce_verifiers()` is a process-global
`Mutex<HashMap<String, String>>`; an entry is inserted when an authorization
query is built and removed only when the code is redeemed, so a consent the
user cancels leaves the verifier resident for the life of the process. Growth
is bounded (the key is the source uid, so a repeat attempt replaces rather
than accumulates), so this is not a leak in the exhaustion sense. But a PKCE
verifier is a secret held in a plain `String`, and neither the `remove` nor
the eventual drop zeroizes it.

Still not fixed, and still for the reason first given: the same process holds
the access token and the user's password in ordinary heap memory too, so this
is one plank of a decision about secret handling across the whole crate rather
than a bug to patch in isolation. Recorded a second time so the decision stays
deliberate.

### F20. A `Slot<T>` was `Sync` for a `T` that must not leave its thread

**Medium, and fixed here, red test first.**
`jmap-backend-core/src/instance.rs`.

This is the narrower half of **F7**, carried as a note through two reports
and dismissed both times as unreachable. It is reachable, and the fix is two
lines. `Slot<T>` derived its `Send`/`Sync` from a `_owns: PhantomData<T>`
marker, so `Slot<T>: Sync` asked for `T: Sync` and nothing more. The note's
own reasoning for calling that harmless was that `clear()` is `unsafe` and
that `Drop` needs `&mut self`.

Both are true and neither closes the hole, because the value that gets
destroyed on the wrong thread does not have to be put there by the thread
that owns the slot. `init` is **safe** and takes `&self`:

1. `Slot<T>: Sync` lets a `&Slot<T>` reach a second thread.
2. That thread builds a `T` of its own and stores it with the safe `init`.
3. The owning thread drops the `Slot`, and `Drop` runs `clear()`, which runs
   that `T`'s destructor on a thread it never belonged to.

No `unsafe` at any call site. Demonstrated before the fix with a
`thread::scope` over `Slot<MutexGuard<'_, ()>>`: it compiled and ran, which
for a `MutexGuard` means unlocking a `pthread` mutex from a thread that did
not lock it. `MutexGuard` is the readiest witness rather than the concern:
the bound is on a `pub` type, so it governs any `T` a later field picks.

**Fixed** by writing the two impls out instead of deriving them
(`unsafe impl<T: Send> Send`, `unsafe impl<T: Send + Sync> Sync`), with the
`PhantomData` kept for drop-check. Pinned by a `compile_fail` doctest that
asserts `Slot<MutexGuard<'static, ()>>` is not `Sync`; confirmed **failing on
the unfixed tree** ("Test compiled successfully, but it's marked
`compile_fail`") and passing after. Every `Slot` in the project holds a
`Mutex`/`RwLock` of owned data, so the tightening narrows no existing use:
`clippy --all-targets -D warnings` is clean for all eight EDS-gated crates,
and `jmap-mail`, `jmap-backend-book` and `jmap-backend-cal`'s existing
`assert_send_sync::<Slot<…>>()` assertions still hold.

The general lesson, worth more than the fix: "the unsafe method carries the
obligation" is not an argument about a type whose *safe* methods can reach the
same state.

### Read and found clean

Each was read against the C it has to match, on this runner, not against a
previous report.

* **Area 1, the two `ESourceConfigBackend` subclasses.** The cross-crate cast
  in `init_class` is the one that could have gone wrong: it writes
  `extensible_type` through `eds_sys::EExtensionClass` into a class struct
  whose parent field `evo-sys` generated. There is no second binding to
  disagree with, because `evo-sys/build.rs` blocklists `_?EExtension[A-Za-z]*`
  and emits `pub use eds_sys::*;`, so both crates name one type.
  `evo-sys/tests/source_config.rs` then pins, against the running type
  system, that `backend_name` begins exactly at `size_of::<EExtensionClass>()`,
  that `parent_uid` follows it, that the four vfunc slots follow in the
  header's order, and that nothing has been appended past `commit_changes`.
  `JmapCalConfig::class_init`'s `allow_creation` write lands in that pinned
  region. Both subclasses declare their dialog type in `class_init_types()`,
  which is what keeps the class initialiser from registering a `GtkBox`
  subclass while GLib holds its class-init lock.
* **Area 2, `get_free_busy_sync`.** The out-parameter's rules are annotated
  after all, at the caller rather than in the vfunc's own header:
  `e-cal-backend-sync.c:707-727` initialises `freebusyobjs = NULL`, declares
  it `(out) (transfer full) (element-type utf8)`, and frees it with `g_free`
  per node then `g_slist_free`. `marshal::free_busy_list` builds exactly that
  (`g_strdup` per node), and `set_out_list` refuses a NULL `dest` rather than
  building a list nobody frees. The three-way `FreeBusyOutcome` keeps the
  out-parameter and the chain-up disjoint: the parent is called only on
  `NothingKnown`, which is the one variant that writes nothing and sets no
  error, so `*out_freebusy` is never written twice and never leaked. The
  chain-up target is right too, and it is subtle: it reads
  `parent_class.get_free_busy_sync` out of the `ECalMetaBackendClass`, which
  is `ecmb_get_free_busy_sync` (installed at `e-cal-meta-backend.c:3550`) and
  not this backend's own slot, so it cannot recurse.
* **Area 3, the named `CamelSasl` subclass.** The registration hazard here
  would be a class table built once, before a provider module registers its
  type. `camel-sasl.c` builds and destroys the table per call
  (`sasl_build_class_table` at every one of `camel_sasl_authtype`,
  `_authtype_list`, `_new`), so a type registered when the `jmap` provider is
  dlopened is found by every later lookup. The heap-allocated, leaked
  `CamelServiceAuthType` is required rather than tidy: `provider_register_
  internal` assigns through `auth->name` and `auth->description`, so the
  `static` this would otherwise be would fault; and the single shared
  allocation is required too, since Camel translates the provider's copy in
  place and two copies would leave `camel_sasl_authtype`'s answer and the
  combo's entry under different names. `authproto` is a `'static` `CStr`,
  which suits a table keyed on the pointer with `g_str_hash`/`g_str_equal`
  and a NULL key destructor.
* **Area 4, the Push wiring's callback lifetimes.** The worker reaches the
  store through a `GWeakRef` and holds a strong reference across a whole
  pass, so the classic shape (a callback outliving its object) is structurally
  excluded rather than argued. The array handling in `refresh_open_folders` is
  the part that could still have been a double free, and is not:
  `camel_store_dup_opened_folders` forwards `camel_object_bag_list`, which
  builds a plain `g_ptr_array_new()` with **no element free function**, so
  unreffing each folder and then `g_ptr_array_free(array, TRUE)` is exactly
  the pattern both functions' own documentation prescribes.
