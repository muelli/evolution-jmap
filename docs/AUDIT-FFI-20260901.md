### F18. The PKCE verifier map holds a secret indefinitely and does not zeroize

Info, unchanged and still open. `pkce_verifiers()` is a process-global
`Mutex<HashMap<String, String>>`; an entry is inserted when an authorization
query is built and removed only when the code is redeemed, so a consent the
user cancels leaves the verifier resident for the life of the process. Growth
is bounded (the key is the source uid, so a repeat attempt replaces rather
than accumulates), so this is not a leak in the exhaustion sense. But a PKCE
verifier is a secret held in a plain `String`, and neither the `remove` nor
the eventual drop zeroizes it.

Still not fixed, and still for the reason first given: the same process holds
the access token and the user's password in ordinary heap memory too, so this
is one plank of a decision about secret handling across the whole crate rather
than a bug to patch in isolation. Recorded a second time so the decision stays
deliberate.

### F20. A `Slot<T>` was `Sync` for a `T` that must not leave its thread

**Medium, and fixed here, red test first.**
`jmap-backend-core/src/instance.rs`.

This is the narrower half of **F7**, carried as a note through two reports
and dismissed both times as unreachable. It is reachable, and the fix is two
lines. `Slot<T>` derived its `Send`/`Sync` from a `_owns: PhantomData<T>`
marker, so `Slot<T>: Sync` asked for `T: Sync` and nothing more. The note's
own reasoning for calling that harmless was that `clear()` is `unsafe` and
that `Drop` needs `&mut self`.

Both are true and neither closes the hole, because the value that gets
destroyed on the wrong thread does not have to be put there by the thread
that owns the slot. `init` is **safe** and takes `&self`:

1. `Slot<T>: Sync` lets a `&Slot<T>` reach a second thread.
2. That thread builds a `T` of its own and stores it with the safe `init`.
3. The owning thread drops the `Slot`, and `Drop` runs `clear()`, which runs
   that `T`'s destructor on a thread it never belonged to.

No `unsafe` at any call site. Demonstrated before the fix with a
`thread::scope` over `Slot<MutexGuard<'_, ()>>`: it compiled and ran, which
for a `MutexGuard` means unlocking a `pthread` mutex from a thread that did
not lock it. `MutexGuard` is the readiest witness rather than the concern:
the bound is on a `pub` type, so it governs any `T` a later field picks.

**Fixed** by writing the two impls out instead of deriving them
(`unsafe impl<T: Send> Send`, `unsafe impl<T: Send + Sync> Sync`), with the
`PhantomData` kept for drop-check. Pinned by a `compile_fail` doctest that
asserts `Slot<MutexGuard<'static, ()>>` is not `Sync`; confirmed **failing on
the unfixed tree** ("Test compiled successfully, but it's marked
`compile_fail`") and passing after. Every `Slot` in the project holds a
`Mutex`/`RwLock` of owned data, so the tightening narrows no existing use:
`clippy --all-targets -D warnings` is clean for all eight EDS-gated crates,
and `jmap-mail`, `jmap-backend-book` and `jmap-backend-cal`'s existing
`assert_send_sync::<Slot<…>>()` assertions still hold.

The general lesson, worth more than the fix: "the unsafe method carries the
obligation" is not an argument about a type whose *safe* methods can reach the
same state.

### Read and found clean

Each was read against the C it has to match, on this runner, not against a
previous report.

* **Area 1, the two `ESourceConfigBackend` subclasses.** The cross-crate cast
  in `init_class` is the one that could have gone wrong: it writes
  `extensible_type` through `eds_sys::EExtensionClass` into a class struct
  whose parent field `evo-sys` generated. There is no second binding to
  disagree with, because `evo-sys/build.rs` blocklists `_?EExtension[A-Za-z]*`
  and emits `pub use eds_sys::*;`, so both crates name one type.
  `evo-sys/tests/source_config.rs` then pins, against the running type
  system, that `backend_name` begins exactly at `size_of::<EExtensionClass>()`,
  that `parent_uid` follows it, that the four vfunc slots follow in the
  header's order, and that nothing has been appended past `commit_changes`.
  `JmapCalConfig::class_init`'s `allow_creation` write lands in that pinned
  region. Both subclasses declare their dialog type in `class_init_types()`,
  which is what keeps the class initialiser from registering a `GtkBox`
  subclass while GLib holds its class-init lock.
* **Area 2, `get_free_busy_sync`.** The out-parameter's rules are annotated
  after all, at the caller rather than in the vfunc's own header:
  `e-cal-backend-sync.c:707-727` initialises `freebusyobjs = NULL`, declares
  it `(out) (transfer full) (element-type utf8)`, and frees it with `g_free`
  per node then `g_slist_free`. `marshal::free_busy_list` builds exactly that
  (`g_strdup` per node), and `set_out_list` refuses a NULL `dest` rather than
  building a list nobody frees. The three-way `FreeBusyOutcome` keeps the
  out-parameter and the chain-up disjoint: the parent is called only on
  `NothingKnown`, which is the one variant that writes nothing and sets no
  error, so `*out_freebusy` is never written twice and never leaked. The
  chain-up target is right too, and it is subtle: it reads
  `parent_class.get_free_busy_sync` out of the `ECalMetaBackendClass`, which
  is `ecmb_get_free_busy_sync` (installed at `e-cal-meta-backend.c:3550`) and
  not this backend's own slot, so it cannot recurse.
* **Area 3, the named `CamelSasl` subclass.** The registration hazard here
  would be a class table built once, before a provider module registers its
  type. `camel-sasl.c` builds and destroys the table per call
  (`sasl_build_class_table` at every one of `camel_sasl_authtype`,
  `_authtype_list`, `_new`), so a type registered when the `jmap` provider is
  dlopened is found by every later lookup. The heap-allocated, leaked
  `CamelServiceAuthType` is required rather than tidy: `provider_register_
  internal` assigns through `auth->name` and `auth->description`, so the
  `static` this would otherwise be would fault; and the single shared
  allocation is required too, since Camel translates the provider's copy in
  place and two copies would leave `camel_sasl_authtype`'s answer and the
  combo's entry under different names. `authproto` is a `'static` `CStr`,
  which suits a table keyed on the pointer with `g_str_hash`/`g_str_equal`
  and a NULL key destructor.
* **Area 4, the Push wiring's callback lifetimes.** The worker reaches the
  store through a `GWeakRef` and holds a strong reference across a whole
  pass, so the classic shape (a callback outliving its object) is structurally
  excluded rather than argued. The array handling in `refresh_open_folders` is
  the part that could still have been a double free, and is not:
  `camel_store_dup_opened_folders` forwards `camel_object_bag_list`, which
  builds a plain `g_ptr_array_new()` with **no element free function**, so
  unreffing each folder and then `g_ptr_array_free(array, TRUE)` is exactly
  the pattern both functions' own documentation prescribes.

### F21 (fixed): a routine credentials lookup was reported as a system fault

**Where.** `jmap-backend-collection/src/create_resource.rs`, `lookup_password`,
reached from `stored_password_of` and so from **both** vfuncs through
`backend.rs`'s `login_for`.

**What.** Every `FALSE` from `e_source_credentials_provider_lookup_sync` went to
`report_critical`, that is to `g_log` at `G_LOG_LEVEL_CRITICAL`. Two of that
call's ordinary outcomes are not faults at all, and both are on paths that then
succeed:

- **An OAuth 2.0 account.** `e_source_credentials_provider_impl_oauth2` matches
  the source through `can_process` (this project registers its own
  `EOAuth2Service`, so `e_oauth2_services_find` answers it), and its
  `class_init` (`e-source-credentials-provider-impl-oauth2.c:91-93`) installs
  `can_process`, `can_store` and `can_prompt` **only**. `lookup_sync` is left at
  the abstract base's default, which is
  `g_set_error_literal (G_IO_ERROR, G_IO_ERROR_NOT_SUPPORTED, "Credentials
  lookup is not supported")` plus `FALSE`
  (`e-source-credentials-provider-impl.c:33-42`). An OAuth 2.0 account has no
  password by construction and `authenticate::login_of` goes on to fetch a token
  and connect, so this arrives on the **success** path of every create and every
  delete such an account performs. OAuth 2.0 is this project's primary
  authentication path.
- **A password account with nothing stored yet.**
  `e_source_credentials_provider_impl_password_lookup_sync`
  (`e-source-credentials-provider-impl-password.c:78-81`) sets
  `G_IO_ERROR_NOT_FOUND`, "Password not found". That is exactly the state
  `stored_password_of`'s own doc comment describes as becoming a credentials
  prompt.

**Why it matters beyond the log.** GLib's critical channel is what a reader
greps when something is broken; a line on it that fires on every successful
create makes the channel useless for the two failures underneath it that really
are faults (the registry server gone, and no credentials provider at all), which
is precisely what that code was trying to record. And `g_critical` is fatal under
`G_DEBUG=fatal-criticals`, a routine way to run `evolution-source-registry` when
debugging: there, "New Address Book" on an OAuth 2.0 JMAP account kills the
registry. No user data is at risk either way, since for the delete the abort
lands before the destroy is sent.

**Fixed** by classifying the failure before the `GError` is consumed. Three
`G_IO_ERROR` codes read as "EDS has no password for this account", which is what
the caller's `None` already means: `NOT_FOUND` and `NOT_SUPPORTED` for the two
cases above, and `CANCELLED`, which is reachable because the vfunc's own
`GCancellable` is passed straight through to libsecret. Those take a
`tracing::debug!`. Everything else, including a `FALSE` carrying no `GError` at
all, keeps the critical: that shape is the provider's own
`g_return_val_if_fail` when it has no implementation to ask, not even the
password fallback (`e-source-credentials-provider.c`, `lookup_sync`), and it is
a genuine fault.

**Red first.** The classification was added as a stub returning `Fault`
unconditionally, which is a faithful encoding of the behaviour before the fix,
and the five tests in `create_resource.rs` were run against it: the two that
state the finding failed and the three that guard against over-widening (another
domain carrying the same code, an unrelated `G_IO_ERROR` code, and no `GError`
at all) passed. The implementation then turned the two red ones green with the
three still passing. The domain is compared as well as the code for the reason
`error.rs`'s `is_authentication_failed` already gives: `G_IO_ERROR` and
`G_DBUS_ERROR` are different enumerations, so a code alone would silence some
unrelated bus failure as "no password".

### What else was checked, and holds

**The two obligations, and the refusal both vfuncs replace.** EDS's
`collection_backend_create_resource()` and `collection_backend_delete_resource()`
each do exactly one thing, `g_task_return_new_error (G_IO_ERROR_NOT_SUPPORTED,
…)`, so the "no chain-up" both modules document is correct and chaining up would
turn a create that worked into a create that reported failure.

**The scratch source's lifetime.** `server_side_source_remote_create_cb`
(`e-server-side-source.c:686-753`) builds it with `e_server_side_source_new` over
`e_server_side_source_new_user_file`, deliberately does not register it, hands it
to `e_source_remote_create` and unrefs its own reference immediately afterwards.
It is alive across the vfunc because the `GTask` behind `remote_create` holds it,
and it survives the vfunc because `e_source_registry_server_add_source` takes a
reference of its own. `adopt_created`'s `scratch.cast()` to `EServerSideSource`
is sound for the same reason the source exists: EDS made it with
`e_server_side_source_new`.

**`write_directory` really does redirect the file.** `server_side_source_write`
(`e-server-side-source.c:1283-1332`) rebases `priv->file` onto
`priv->write_directory` on every write whose data changed, so the created child's
`.source` lands in this collection's cache directory rather than in the registry
user directory EDS minted it in, which is what makes a created child claimable by
`collection_backend_load_resources` on the next start and what makes removing the
account take it along. The write itself is not left to chance:
`e_source_registry_server_add_source` ends on `e_source_changed (source)`, whose
comment says it is there "to ensure the source data gets written to disk, since
the ESource is exported now… could be racy otherwise if this function is called
from a worker thread", which is exactly the thread this vfunc runs on.

**The child source outlives its own removal.**
`server_side_source_remote_delete_sync` is dispatched on the child itself and
passes that same child to the vfunc, so the `GTask` behind `remote_delete` holds
a reference throughout. `remove_source`'s `e_source_remove_sync` therefore cannot
be the last one: it drops the registry's reference, not the caller's, and nothing
touches `child_source` afterwards (the log line reads the owned `Doomed`, not the
source). EDS does not remove the source itself after a successful vfunc, so the
documented obligation is discharged exactly once.

**The destructive ordering.** Destroy first, remove second, which is what
`delete_resource.rs` documents and what the error handling turns on. Worth
recording that `e_source_remove_sync` runs `g_task_set_check_cancellable (task,
TRUE)`, so a user who presses Stop during the network destroy gets
`DeleteError::Stale` rather than a silent half-delete, which is the recoverable
direction.

**Identity gating.** `doomed_of` refuses every source that is not one this
backend wrote, reading through the same `resource_id_of` `dup_resource_id`
answers with, so the string a destroy acts on is the one EDS knows the child by.
`extension_if_present` is the right primitive here and not caution:
`e_source_get_extension` creates what it cannot find, and these two vfuncs are
handed sources belonging to other parts of Evolution. The account the destroy is
sent to is resolved through `CollectionLayout` exactly as discovery and create
resolve it, so a delete cannot name an id to an account in which that id is some
other collection.

**Cancellation.** `observe` is installed after `login_for` in both vfuncs, which
at first looks like a gap, and is not: the credentials lookup and the OAuth 2.0
token fetch inside `login_of` both take the raw `GCancellable` and are cancelled
natively by it, so nothing above the JMAP client is left uncancellable.
`Cancellation`'s fields are declared scope-then-bridge so the thread stops
observing the flag before the handler feeding it is disconnected, and a
`g_cancellable_connect` that returned 0 (a NULL or already-cancelled cancellable)
is handled in `Drop`.

**Error out-parameters.** Both vfuncs set the `GError` only on paths they then
return from, so `guard_bool`'s own panic error can never overwrite one; and
`set_raw_gerror` has done a real overwrite check since `8b2cf3a` (see §7, F9),
which closes that structurally rather than per call site. `lookup_password`
frees the `GError` on the success-with-error path and the `ENamedParameters` on
every path that got one.
