## 3. Audited and clean

### 3.1 `jmap-backend-collection`'s `login_fingerprint` fix (item 66 follow-up)

Already shipped `6dd4f401` (item 66) with its own tests; re-read here as part
of this delta. `login_fingerprint`'s `unsafe fn` contract (a valid `ESource`,
read-only, nothing outlives the call) is upheld at both call sites in
`backend.rs` (`populate`'s and `on_account_changed`'s), both under a
"valid account source, only read from" safety comment matching the contract.
The hash is built from `Debug` rather than a hand-picked field list
(deliberately, per the module doc, so a new `Server` field joins automatically),
which is a correctness choice, not a safety one — nothing here is `unsafe`
beyond the FFI reads already covered by item 66's own audit. Tests cover the
same-fingerprint/different-fingerprint/zeroed-state matrix directly against
`AccountWatch`, not just through the FFI surface.

### 3.2 `jmap-mail`'s `initial_setup_sync` (item 69)

`save_role`'s `g_hash_table_insert` pairs a freshly `g_strdup`'d key and value
with the table's own `g_free`/`g_free` destroy functions (Camel's own wrapper
creates the table this way), so ownership transfers cleanly: no leak, no
double free, and the `CString`/`c_string` temporaries used to build the
`g_strdup` source are dropped only after `g_strdup` has already copied them.
`tree_holding`'s predicate closure is pre-existing shared code (reused, not
new). Four tests in `jmap-mail/tests/folders.rs` cover both roles present,
one role present, and neither role present (the documented
"returns TRUE and populates nothing" contract).

### 3.3 `jmap-mail`'s `get_message_cached`/`cached_message` (item 70)

`get_message_cached` takes no `camel_folder_lock`, matching the vfunc's own
documented contract ("not being blocked by the folder's lock"); the shared
`cached_message` helper is the same lookup `get_message_sync` used to inline,
now called from both, with identical behaviour (verified by reading both call
sites, not assumed from the commit message). A parse failure is a silent miss
in both, matching the vfunc's "NULL for a miss, not an error" contract — there
is no `GError` out-parameter on `get_message_cached` to report one through
even if it wanted to.

### 3.4 `jmap-mail`'s `search_body_sync` (item 71)

Re-read independently of the item's own opus-5 escalation writeup.
`pooled_uid_array` builds a `GPtrArray` with `g_ptr_array_new_with_free_func
(Some(free_pstring))`; every element is a `camel_pstring_strdup` result
(pool-interned, so the temporary `CString` built to call it can be dropped
immediately after — `camel_pstring_strdup` copies), and `free_pstring` pairs
it with `camel_pstring_free`, the same pairing IMAPX and Camel's own base
implementation use for this exact array shape (documented in the module,
confirmed against `camel-data-cache.h`-adjacent Camel string-pool
conventions). `body_filter` refuses a term of only empty words (`None`,
reported as "cannot search") rather than misreading it as "matches
everything"; three tests exercise the one/many/empty-word cases directly.
The vfunc's null/refusal paths (`out_uids` NULL, no mailbox, no store
connection) all fail closed rather than answering an empty array that would
be read as an authoritative "matches nothing".

### 3.5 `get_destination_address` wired into `jmap-backend-book` and
    `jmap-backend-cal`

Both mirror `jmap-backend-collection`'s already-audited implementation
(`c4834d6c`, prior report) byte-for-byte in logic: `e_backend_get_source`
NULL-checked, `destination_address` (unchanged shared helper, only its
`Display` impl gained i18n wrapping in this delta) read once, `host`/`port`
out-parameters only ever written on the success path with ownership of the
`dup_string`-allocated host transferred to EDS's `g_free`. Both carry their
own `class_init_replaces_the_default_get_destination_address_rather_than_leaving_it`
test, which compares the installed vfunc pointer against the real linked
parent class's default — not a compile-only assertion, an actual runtime
check against `evolution-addressbook-3.0`/`evolution-calendar-3.0`. The vfunc
slot offset each writes through (`EBookMetaBackendClass` -> `EBookBackendSyncClass`
-> `EBookBackendClass` -> `EBackendClass` for book; the calendar equivalent
for cal) is exercised by that same test, so a wrong offset would show up as
a wrong function pointer at parent lookup, not a silent corruption.

### 3.6 `jmap-mail`'s folder-lock fix in `transfer_messages_to_sync`

The new `FolderLock` RAII guard (`camel_folder_lock`/`_unlock`, released on
`Drop`) closes a real race: `camel_folder_transfer_messages_to_sync`'s own
wrapper does not lock its source folder the way `refresh_info_sync`/
`synchronize_sync`/`expunge_sync` do, so nothing previously serialised a
transfer's `camel_folder_summary_remove_uid` against a concurrent refresh's
reconciliation of the same summary. The claim that Camel's own three
vfunc-dispatch wrappers take this lock is stated as checked directly against
evolution-data-server 3.52.3's `camel-folder.c` source, not assumed from the
header (this runner's own headers carry no function bodies to check
against). Best available evidence for the fix's own correctness is
`jmap-mail/tests/transfer_race.rs`, which drives the actual race against the
*real* linked `camel_folder_refresh_info_sync` and
`camel_folder_transfer_messages_to_sync` concurrently on one real
`CamelFolder`, gated so the refresh's `Email/query` completes for real before
its delivery is held open — this is real linked-library evidence, not a
model of Camel's locking, and it passes, including no deadlock (a
non-recursive lock taken twice by the same thread would hang the test, not
silently pass). `RAII`-on-drop covers every one of the vfunc's several early
returns, which the module doc calls out as the reason a plain
lock/unlock-by-hand was rejected.

### 3.7 `jmap-config`'s credential-name detection fix

`account.rs`'s `apply` previously checked only the generic `OAUTH2_METHOD`
alias against `auth_method`, while `backend.rs`'s setup combo and
`config_lookup.rs`'s discovery both actually write `oauth2_service::NAME`
("JMAP") into that field — so every real OAuth 2.0 account fell through to
the password branch and got no `credential-name`, silently defeating the
eds#663 groundwork item 73 describes as inert-but-present. Fixed by checking
both. Pure Rust string comparison, no new unsafe surface; the surrounding
`unsafe fn apply`'s existing contract is unaffected.

### 3.8 `jmap-config`'s bracketed-IPv6 authority parser

`parse_target` previously used `rsplit_once(':')` guarded by
`!bare_host.contains(':')` to tell a host:port pair from a bare (unbracketed)
IPv6 literal, which cannot distinguish `[::1]:8443` from a bare IPv6 literal
at all — the RFC 3986 bracket form was never handled, and every one of its
colons would defeat the guard. Fixed with an explicit bracket-stripping
branch tried first; malformed brackets (`[::1` unterminated, `[]:8443` with
an empty host, a non-numeric port after `]:`) all fall through to `None` via
`?`/explicit checks rather than being misparsed. Two new tests cover the
with-port and without-port bracketed cases; `secure` (derived from the
`https://`/`http://` scheme prefix, unaffected by this change) still governs
the TLS-by-default rule independently of the authority-parsing fix.

### 3.9 `jmap-mail`/`jmap-mail-sync` protocol-hardening fixes

`search_sexp.rs`'s `translate_bool` now refuses `(and)`/`(or)` with no
arguments (RFC 8620 SS5.5 defines no `FilterOperator` behaviour for an empty
`conditions` array) instead of building one to send to the server; two tests
cover the bare and nested cases. `jmap-mail-sync::message_mailboxes` now
refuses a `mailboxIds` entry a server spelled `false` instead of omitting the
key, rather than the prior reading that counted it as membership regardless
— the prior reading could turn a message truly filed in one mailbox into an
update that removes its last true entry, which a conforming server refuses
outright. Both are pure-Rust parser/protocol fixes with test coverage of the
hostile shape; no FFI surface.

### 3.10 `example-module`'s EUIManager port (item 74), read independently of
     its own delivery writeup

Read `m-calendar-ui.c` and `m-msg-composer-extension.c` in full against this
delta's diff (`m-mail-ui.c`/`m-shell-view-extension.c`/`m-utils.c` share the
same pattern, spot-checked rather than read line by line, given the time
budget for this session). Findings:

- Both files' `EUIActionEntry` tables and `<eui>` merge strings match the
  pattern `jmap-ui`'s snooze/send_later extensions already established (own
  action group per extension, `e_ui_manager_add_actions_with_eui_data`,
  idempotent re-entry guarded by `e_ui_manager_get_action_group` returning
  non-NULL on a second call).
- The `"update-actions"` signal `m_calendar_ui_init`'s EUIManager branch
  connects is confirmed, independently of this item's own writeup, to exist
  under the identical name and zero-argument arity on both Evolution eras:
  `jmap-ui/src/snooze/shell_ext.rs`'s own module doc states this was checked
  live ("connecting the old `\"toggled\"` the old way logs a GLib-CRITICAL
  ... update-actions ... the one signal both eras keep"), and this port's
  `g_signal_connect` call shape (instance, signal name, callback, user data)

- `m_calendar_ui_update_actions_cb`'s pre-3.55 branch (unchanged by this
  delta except for the `calendar_has_selected_event` extraction) has a

- Struct-layout correctness for `EUIActionEntry`'s field order (the same
