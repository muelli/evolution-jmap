## 1. Findings

### F33 (LOW, fixed): JSContact unsigned integers from the server wrapped instead of being rejected

`jmap-proto/src/contacts.rs`. `deserialize_optional_u32` (behind
`Directory.listAs` and `PersonalInfo.listAs`, added in this delta by
`e3578460`) cast a JSON number with `value as u32`, so `4294967297` arrived
as `1`, while the same number written as a string went through
`str::parse::<u32>` and was rejected. The pre-delta `LanguagePref`
visitor had the same cast on both its `u64` and `i64` paths, so `-4`
arrived as `4294967292`; and the new `Anniversary::pref()` accessor
truncated the same way. RFC 9553 types all of these as `UnsignedInt`, so
none of these values is valid; a hostile server could make one wrap into a
small, plausible preference or sort order instead of failing. Severity
LOW because no shipped code path reads any of the four today (`jmap-vcard`
and the sync crates never consult them), so this is latent, not exploited.

Fixed in `9145f653`: every path uses `u32::try_from`, the deserializers
reject, and `Anniversary::pref()` answers `None`. Red-first test
`an_out_of_range_unsigned_int_is_rejected_not_wrapped`
(`jmap-proto/tests/contacts.rs`). One existing assertion in
`jmap-proto/tests/mutation_contacts.rs` pinned the wrapped `-4` value
itself; it now asserts the rejection, which still kills the mutant it was
written for.

### F32 (INFO, now fixed): nested `jmap_tracing_capture::capture` dropped the outer scope

Carried open from `docs/AUDIT-FFI-20261015.md`, where it was left because
item 103's lock covered the crate; that item has since closed. Fixed in
`30733e6f`: `capture` saves the thread's previous scope and a drop guard
restores it, which also keeps a panicking closure from leaving the scope
set for the next test on that thread. Red-first test
`a_nested_capture_hands_the_scope_back_to_the_outer_one`
(`jmap-tracing-capture/tests/isolation.rs`); before the fix the outer
buffer held `["1"]` instead of `["1", "3"]`.

## 3. New-code audit

### `jmap-backend-core/src/connect.rs`: test of `no_source_gerror`

The new unsafe block dereferences a `GError` that `e_client_error_create`
just returned (asserted non-NULL first), reads `domain`, `code` and
`message` through `marshal::read_string`, and frees it exactly once with
`g_error_free`. The function under test is unchanged. CLEAN.

### `eds-sys/build.rs`: `e_extensible_.*` added to the bindgen allowlist

Brings in `e_extensible_get_type`, `e_extensible_load_extensions` and
`e_extensible_list_extensions`. No new struct layouts (`EExtensible` is an
opaque interface type), so no layout test is owed. Only the jmap-ui test
below calls them; `list_extensions` (transfer container) has no caller.
CLEAN.

### `jmap-ui/tests/interface_extension.rs`: an `EExtension` typed on an interface

Test-only GObject subclassing through `jmap_backend_core::subclass`. Read
in full. Both probe instance and class structs are `#[repr(C)]` and lead
with their parent's struct; the interface is registered with
`class_size = size_of::<GTypeInterface>()` and a `GObject` prerequisite,
matching `G_DEFINE_INTERFACE`. `constructed` chains to the parent class
looked up by `g_type_class_peek` on `e_extension_get_type()`, the right
class for an `EExtension` subclass, and stores only the extensible's
address. `e_extension_get_extensible` is transfer none and is not
retained. Each probe object is unreffed once, after the observation; the
extensions it owns go with it. The extension's `class_init` calls only
the file's own `probe_interface()`, which is already initialised by then
(the implementer's `interfaces()` ran first) and in any case registers a
type rather than taking `REGISTRATION`; the one `#[test]` in the binary
makes it single-threaded, so the foreign-`get_type` cycle item 110 is
about cannot arise here. CLEAN.

### `jmap-proto/src/contacts.rs`: RFC 9553/9610 shape alignment (`e3578460`)

Untrusted-input surface, read in full. Besides F33: the `@type`
deserializers for `ContactCard`, `SchedulingAddress` and `Directory` accept
any string and fail only on a non-string, which is what the previous
`Option<String>` did. Serialisation always writes the canonical `@type`.
`parse_iso_partial_date` only rewrites a string date that splits into
integer parts and otherwise sends the string back unchanged, so no date
is dropped; it does not range-check month or day, so a malformed local
string becomes an out-of-range `PartialDate` the server will reject on
`set` rather than a string it would also reject: no change in outcome.
`AddressBook.mayDelete` is now never serialised, correct for a
server-set property. No panics on any input: there is no indexing outside
the `parts.len()` checks. CLEAN apart from F33.

### `tests/functional/cal-attendees-client.c`, `cal-attendees-remote-client.c`

New EDS acceptance-test clients (items 108 parts 1 and 3). Every
`ICalComponent` and `ICalProperty` reference is released once;
`first_vevent` returns an owned reference either way and the libical-glib
child keeps its parent alive across the `g_object_unref (read_back)`; the
remote client's list is freed with `g_slist_free_full` after its one
extra ref is dropped. The early-error `return`s leave the registry, source
and client referenced, but each is a process exit straight after, so
nothing outlives it. CLEAN.

### `jmap-functional/tests/live-stalwart-calendar-attendees*.rs`

Credentials come from `JMAP_LIVE_SERVER_WRITE_USER`/`_PASSWORD` and reach
the client only through the test's own session store; none is printed,
including in the skip message. CLEAN.
