## 1. Findings

### F30 (fixed): `CalendarEvent/parse`/`ContactCard/parse` silently discarded every event or card past the first in a multi-entry blob

**Severity: low** (no production caller yet — `grep -rn "event_parse\|contact_card_parse"`
across every crate finds only test/example call sites, same absence of a
live path F29 had. Recorded and fixed now because the defect is real and
reachable the moment any future caller imports an arbitrary user-supplied
`.ics`/`.vcf` file, which is exactly what these two methods exist for).

**Where** `rust/crates/jmap-client/src/calendars.rs::event_parse` and
`src/contacts.rs::contact_card_parse`, both added their array-unwrap step in
this delta's Finding 13/14/15 tolerance commits (`a84e60a9`, `36e859d8`).

**Why it is a real bug, not a theoretical one.** Both methods' typed response
models exactly one parsed value per blob id
(`CalendarEventParseResponse::parsed: BTreeMap<Id, CalendarEvent>`,
`ContactCardParseResponse::parsed: BTreeMap<Id, ContactCard>`), but the new
code's job was tolerating Stalwart wrapping that one value in a JSON array
instead of sending it bare. The pre-fix code did this unconditionally:

```rust
let mut arr = match std::mem::replace(val, Value::Null) {
    Value::Array(arr) => arr,
    _ => unreachable!(),
};
*val = arr.drain(..).next().unwrap_or(Value::Null);
```

— take the array's first element, silently discard the rest, with no error,
no log, nothing a caller could detect. Confirmed live against real Stalwart
(`stalwart-runner`, a throwaway `agent-ffi-audit.test` domain/account seeded
for this audit) that the array is not always one element long: uploading an
`.ics` blob containing two distinct top-level `VEVENT`s (different `UID`s)
and calling `CalendarEvent/parse` returns

```json
"parsed": {"<blobid>": [{"uid":"probe-multi-1", ...}, {"uid":"probe-multi-2", ...}]}
```

one array element per event. A real-world multi-event `.ics` (a calendar
export bundling several appointments in one file, or a recurring series
where distinct `UID`s are used for separate occurrences — any multi-`VEVENT`
blob without a shared `UID`) parsed through this client would have silently
returned only the first event and reported success, with the rest simply
gone. The exact same unwrap shape was also added to `contact_card_parse`,
though probing a two-`VCARD` blob there found a different, non-actionable
server-side limitation instead (see "Also checked" below) — the client-side
risk is identical in principle even though this particular probe found
Stalwart's own vCard handling drops the second card even earlier, before any
array is formed.

**Fix** (this branch, one commit): both call sites now go through a shared
`demote_multi_element_parsed_blobs` helper (`contacts.rs`, reused by
`calendars.rs`): an array of length exactly one is still unwrapped
transparently (the common, harmless case this tolerance exists for); an
array of length zero or more than one moves its blob id out of `parsed` and
into the response's existing `notParsable` field instead of letting only one
element survive silently. `notParsable` already exists in both proto types
for exactly this "the server can't name you a single event/card at this
id" case, so no API shape change was needed.

**Evidence.**
- `rust/crates/jmap-client/tests/stalwart_tolerances.rs`:
  `finding_13_calendar_event_parse_reports_multi_event_blob_as_not_parsable`,
  a two-element-array mock fixture built from the live wire shape above.
  Confirmed red before the fix (stashed `calendars.rs`/`contacts.rs`, kept
  the test): panics with "a multi-event blob must not surface as a single
  parsed event". Green after.
- `rust/crates/jmap-client/tests/live_server.rs`:
  `calendar_event_parse_reports_multi_event_blob_as_not_parsable_through_the_real_api`,
  `#[ignore]`d, run for real against `stalwart-runner` this session (not just
  compiled): uploads a genuine two-`VEVENT` blob and asserts `notParsable`
  names it. Passed, alongside the existing six `calendar_event*` live tests
  (no regression).
- All 17 pre-existing `stalwart_tolerances.rs` tests (including the two
  other Finding 13 tests and both Finding 15 `ContactCard/parse` tests, which
  exercise the single-element-array case this fix must keep transparent)
  pass unchanged.

**Also checked, not a client-side gap:** whether `ContactCard/parse` ever
produces a multi-element array the same way. Uploaded a `.vcf` blob with two
concatenated `VCARD`s (distinct `UID`s) to real Stalwart: it returned a bare
single-object `parsed` value for the first card only, with no array and no
indication the second card existed at all — the second card is dropped
server-side, before this client's code ever sees it. Not a new finding
proper (no RFC text found naming a required multi-card-per-blob contract for
`ContactCard/parse`, unlike the `CalendarEvent/parse` case where Stalwart's
own answer confirms it parsed both events and chose to report both), but
worth a `RFC-SUSPECT` line per the standing directive, below.

## 4. RFC-SUSPECT (recorded per the standing directive, not adjudicated here)

`ContactCard/parse` against a `.vcf` blob containing two concatenated
`VCARD` components (distinct `UID`s) returns a single `Card` for the first
one only, under a bare (non-array) `parsed` value, with no `notParsable`,
no error, and no trace the second card existed. `CalendarEvent/parse` on the
structurally equivalent multi-entry case (two `VEVENT`s in one blob) *does*
parse and report both, via the array-wrapping this report's F30 is about.
Neither RFC 9610 (JMAP Contacts) nor the `ContactCard/parse` draft text
available here was checked closely enough to say definitively which
behaviour, if either, is specified for a multi-card blob; recorded as
suspect because the inconsistency between the two `/parse` methods'
handling of "more than one thing in the blob" suggests the vCard path may
simply not have been built to notice, not that this is an intentional
design choice. Recorded as `RFC-SUSPECT` per the standing directive; not
filed, not further investigated this session.
