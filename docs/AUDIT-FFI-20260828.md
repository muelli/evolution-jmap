authentication failure that the operator sees as a repeating consent window —
the symptom ROADMAP items 15, 17, 20 and 22 are all chasing.

### F16 — the three `prepare_*` overrides ran EDS's default a second time

`interface_init` saved the incoming vtable slot into a global `OnceLock` and
each override then called it, on the stated belief that the slot "arrives
pre-filled with EDS's default … Keep the default reachable and chain to it".
Half of that is true and half is not:

* **True:** `e_oauth2_service_default_init` really does install the defaults
  into the slots — `e-oauth2-service.c:320`, `:322`, `:324` assign
  `eos_default_prepare_authentication_uri_query`,
  `eos_default_prepare_get_token_form` and
  `eos_default_prepare_refresh_token_form`. So the saved pointer was genuinely
  EDS's default, not NULL. (`EOAuth2ServiceBase` is not in the way:
  `e-oauth2-service-base.c:34` is a plain `G_DEFINE_ABSTRACT_TYPE` over
  `E_TYPE_EXTENSION` and implements no interface, so ours is the first
  `interface_init` in the chain and the vtable it sees is the interface's own.)
* **Not true:** that the slot is a chain link. Each public wrapper calls its
  `eos_default_*` body **itself, directly and unconditionally**, *before*
  dispatching to the vtable — `:648`, `:822`, `:895` — and consults the slot
  only afterwards, skipping it when it still literally holds that same default
  (which is the anti-recursion guard, not an "only if unfilled" guard).

So the default ran twice on every authorization request and every token
grant. EDS's own services are the convention this deviated from, and they are
unambiguous: `eos_google_prepare_authentication_uri_query`
(`-google.c:185`) sets `scope` and `include_granted_scopes` and nothing else;
`eos_outlook_prepare_authentication_uri_query` / `_prepare_refresh_token_form`
(`-outlook.c:152`, `:163`) likewise. Neither saves the default; neither calls
it. **The slot is an additive hook.**

**Impact today: benign.** `e_oauth2_service_util_set_to_form`
(`e-oauth2-service.c:1947`) is insert-or-remove, so running the default twice
lands the same table, and `take_to_form` (`:1978`) hands the table ownership of
each `login_hint` so the displaced one is freed rather than leaked. What it did
cost was doubling every `get_client_id` / `get_client_secret` /
`get_redirect_uri` dispatch (each of which takes the extension's mutex) on the
authorization path.

**Impact latent: medium.** The safety of the double call rests entirely on
every present *and future* `eos_default_*` body being idempotent. One that
appended to a list, or generated a nonce, or counted, would corrupt the request
silently — and because the doubling is invisible through the wrapper (both
shapes produce the same table), no test written against the public entry point
can ever see it. That is exactly what happened here: the existing
`prepare_authentication_uri_query_names_the_registered_scope` asserted
`response_type` is present with the failure message "chaining to EDS's default
was lost — the standard query is gone", and that assertion **could not fail
either way**, because the wrapper supplies `response_type` whether or not we
chain. A guard that cannot fail is worse than no guard.

**Fixed.** `interface_init` now installs the three overrides without saving
anything; the three `OnceLock<unsafe extern "C" fn(…)>` statics and the three
raw function-pointer calls are gone (a net reduction in this file's unsafe
surface, since calling a function pointer recovered from a C vtable was the
riskiest construct in it). The module docs gained an "additive hook, not a
chain link" section stating the rule and citing the lines, and the third bullet
of "What is filled, and what is not" — which still claimed "**JMAP has nothing
to add**" to these five slots, written before scope/resource/PKCE were known to
be needed — was corrected rather than contradicted.

**Red first.** `tests/oauth2_service.rs` gained
`the_authentication_query_slot_adds_only_this_services_own_keys` and
`the_token_form_slots_add_only_this_services_own_keys`, which reach the slot
the way the wrapper does (`g_type_interface_peek` on the class's own interface
vtable — *not* `g_type_default_interface_ref`, which would hand back the
interface's defaults) and invoke it directly. Dispatching directly is the whole
point: it is the only vantage from which the difference is observable at all.
Both failed on unmodified master — "the slot re-ran EDS's default:
`response_type` is the wrapper's to set", and the same for `code` on the token
form — and pass after. The existing wrapper-level tests were left in place,
unmodified except for that one misleading failure message, and stayed green
throughout, which is the independent confirmation that the wrapper really does
supply the base keys on its own.

### F17 — an unredeemable PKCE challenge was sent silently, and its failure was logged at DEBUG

**Fixed (session 5).** Two independent problems, in the two functions that
share PKCE state:

`prepare_authentication_uri_query` added `code_challenge` and
`code_challenge_method=S256` to the query **unconditionally**, and only then
stashed the verifier — and stashed it only `if let Some(ref uid) = uid`. If
`read_string(e_source_get_uid(source))` answered `None`, the request carried a
challenge whose verifier was never kept, and the code exchange that follows
was guaranteed to fail with `invalid_grant` (RFC 7636 §4.6 obliges the server
to reject it). **Fix:** the two halves are now all-or-nothing — the challenge
and its stash happen together, gated on the same `if let Some(ref uid) = uid`,
so a uid-less source falls back to sending no challenge at all (a well-defined
request every deployment this project targets already tolerates, being EDS's
own default query with nothing added) rather than one that can never be
redeemed. **Not reachable by a test on this runner**, unchanged from the
original finding: `ESource` always has a uid in practice (`e_source_new*`
generates one when the caller passes none), and there is no way to build a
uid-less one through EDS's public API to drive a red test with. Recorded as a
structural fix rather than a proven regression test.

The second half was reachable and mattered more, and is what actually got a
red test: `prepare_get_token_form` finding no stashed verifier set
`has_pkce = false` and proceeded at `tracing::debug!` only. That is the
failure mode that turns into the operator's repeating consent window (items
15/17/20/22), and the journal line that would attribute it was (a) below the
level anything is likely to be capturing and (b) indistinguishable from the
legitimate "this deployment never used PKCE" case. **Fix:** a
`tracing::warn!` now fires whenever `prepare_get_token_form` finds no stashed
verifier, naming that a challenge may already have been sent and that the
server is expected to reject the exchange — the `debug!` line is unchanged
and still carries `has_pkce` for the normal case. This is the same class of
work ROADMAP item 20 (3) asks for — "make every consent escalation traceable
… so the operator's next sighting is attributable from the journal alone" —
and item 22 (3)'s "surface it as an ERROR, never as consent".

**Red first.** `tests/oauth2_service.rs` gained
`a_missing_pkce_verifier_at_redemption_is_logged_at_warn_level`: a minimal
`tracing::Subscriber` (`LevelCapturingSubscriber`, recording only each
event's level — enough for this, unlike `tracing_writes.rs`'s fuller
field-capturing one) proves a normal redemption emits no `WARN`, and a second
redemption of the same code (single-use — the verifier is already gone,
exactly the reachable trigger for "no stashed verifier") emits one. Failed on
unmodified master (only `Level::Debug` captured) before the fix, confirmed by
stashing the source change and rerunning; passed after. One pre-existing test,
`jmap-config/tests/tracing_writes.rs`'s
`prepare_authentication_uri_query_and_token_form_trace_structured_fields`,
asserted the now-removed `pkce_challenge_method=S256` field on the query side;
updated to assert `has_pkce=true` instead, which is the same information the
token-form side already logged under that name — the two sides are now
symmetric.

### F18 — the PKCE verifier map holds a secret indefinitely and does not zeroize

Info. `pkce_verifiers()` is a process-global `Mutex<HashMap<String, String>>`.
An entry is inserted when an authorization query is built and removed only when
the code is redeemed, so a consent the user cancels leaves the verifier
resident for the life of the process. Growth is bounded — the key is the source
uid, so a second attempt on the same account replaces rather than accumulates,
and the map can never exceed the number of accounts — so this is not a leak in
the exhaustion sense. But a PKCE verifier is a secret, it is held in a plain
`String`, and neither the `remove` nor the eventual drop zeroizes it.

Not fixed here, and arguably not worth fixing on its own: the same process
holds the *access token* and the user's password in ordinary heap memory too,
so this would be one plank of a much larger decision about secret handling
across the whole crate. Recorded so the decision is made deliberately rather
than by omission.

## 3. What was read and found clean

Everything below was read adversarially against the same EDS sources and no
finding was raised. Recorded so the next session on this thread does not redo
it.

* **The seven `const gchar *` vfuncs** (`get_name`, `get_display_name`,
  `get_client_id`, `get_client_secret`, `get_authentication_uri`,
  `get_refresh_uri`, `get_redirect_uri`). Each answers either a `'static`
  `CStr`, gettext's own storage, or a borrow of `oauth2::Fields`. The borrowed
  case is the one that could dangle, and `oauth2.rs`'s discipline holds up:
  `Fields::set` performs no write at all when the value is unchanged (so a
  pointer already in flight keeps its allocation) and moves a displaced value
  into `Fields::retired` rather than freeing it (so a pointer into the old
  value stays valid until the extension is finalized). Moving a `CString` into
  that `Vec` moves the pointer and not the bytes, so a later reallocation of
  the vector does not invalidate anything either. The documented lifetime —
  "valid for as long as the extension is" — is actually what the code
  delivers, and it is at least as strong as what EDS's own
  `eos_google_get_client_id` promises for the same vfunc.
* **The mutex is not what upholds that lifetime, and the file says so.** The
  lock is released before `borrowed` returns. That is correct and unavoidable
  (a `const gchar *`-returning vfunc has no "done with it" callback), and it is
  the retire discipline, not the lock, that makes the pointer safe. The doc
  comment already states this precisely; the audit's job here was to check the
  code matches, and it does.
* **`g_hash_table_replace` vs. the table's destroyers.** Every key and value we
  put into a `uri_query`/`form` table is a fresh `g_strdup`, which the table
  frees — the contract `e_oauth2_service_prepare_authentication_uri_query`'s
  own docs state ("both key and value to be newly allocated strings, which will
  be freed together with the hash table or when the key is replaced").
  `replace` rather than `insert` also replaces the key, which is the right
  choice given both halves are freshly allocated.
* **Temporary lifetimes at the `g_strdup` call sites.**
  `g_strdup(cstring_lossy(&…).as_ptr())` is the shape that would dangle if the
  `CString` temporary dropped before `g_strdup` read it. It does not: a
  temporary in a function call's argument lives to the end of the enclosing
  statement, and `g_strdup` copies within it.
* **`can_process` / `guess_can_process` / `extract_authorization_code` /
  `extract_error_message` left unfilled.** Correct, and for the reason the
  module docs give. `can_process`'s default matches `[Authentication] method`
  against `get_name()`, which is what this service wants;
  `tests/oauth2_service.rs` already drives both the matching and non-matching
  cases through `e_oauth2_services_find`.
* **The per-uid keying of `pkce_verifiers()` across processes.** The concern is
  that the authorization half and the redemption half could run in different
  processes, in which case the map would silently never hit. They do not: the
  only EDS caller of `prepare_get_token_form` is
  `e_oauth2_service_receive_and_store_token_sync` (`e-oauth2-service.c:1435`),
  which the credentials prompter drives, in the same process that built the
  query. `prepare_refresh_token_form` — the one that *does* run in the registry
  and factory processes — touches no PKCE state. The file's claim is right.
* **`OnceLock` set-once under dynamic type re-registration.** Moot now that the
  three statics are gone, but it was checked before deciding: a `GTypeModule`
  type can be unloaded and re-initialized, at which point `interface_init` runs
  again and `let _ = OnceLock::set` silently keeps the first pointer. That was
  harmless (the target is a static function in libedataserver, which is never
  unloaded), but it is one fewer thing to reason about now.
* **`unsafe impl ObjectSubclass for Service` / `InterfaceImpl for Vtable`.**
  Both structs are `#[repr(C)]` and lead with the parent's instance/class
  struct, and `eds-sys/tests/oauth2.rs` pins the interface's shape against the
  live type. `Service` carries no state of its own, so there is no
  `instance_init`/`finalize` pairing to get wrong.

## 5. Area (5): `jmap-backend-core` oauth2/connect classification (session 6)

Scope, per ROADMAP item 21's own text: the classification code that decides
*why* a silent OAuth 2.0 token refresh failed and *what* `connect_sync`/
`authenticate_sync` report back to EDS — `jmap-backend-core/src/oauth2.rs`
(`classify_failure`, `is_secret_store_failure`, `is_secret_not_found`,
`access_token`) and `connect.rs` (`ConnectError`, `LoginError`,
`auth_result`, `reclassify_oauth2_rejection`, `finish_connect`), plus the
collection backend's sibling in `jmap-backend-collection/src/authenticate.rs`
(`login_of`, `LoginError`, `finish_fan_out`). Unlike areas (1)–(4), this code
is pure Rust logic reading a caller-guaranteed-valid `GError*`'s
domain/code/message fields — no ownership transfer, no lifetime juggling, no
GObject re-entrancy — which is why it was tractable this session rather than
carried forward with the other three.

**Motivation, beyond item 21's own ordering:** this is exactly the code
ROADMAP item 22 (the stale shell `OAuth2Support` D-Bus proxy, captured live
2026-08-28) would have to route through, so the audit doubled as a check on
whether item 22's symptom is a classification bug here or something outside
this code's reach.

### Read and found clean

* **`is_secret_store_failure`/`classify_failure` already treat *every*
  `g_dbus_error_quark()` domain error — including `SERVICE_UNKNOWN` (code 2,
  item 22's own observed code) and `NAME_HAS_NO_OWNER` — as
  `SilentRefreshFailureReason::SecretStoreFailure` /
  `ConnectError::SecretStore`, which `ConnectError::auth_result()` maps to
  `E_SOURCE_AUTHENTICATION_ERROR`, never `REQUIRED`.** Traced through both
  consumers: `jmap-backend-core::connect::connect_with` (book/cal) and
  `jmap-backend-collection::authenticate::login_of` (the collection backend,
  via `LoginError::Credentials(_).auth_result()` delegating to the same
  function). Confirmed by the existing
  `dbus_timeout_and_transport_errors_are_secret_store_failures` test, which
  already parametrizes over code `2` (`SERVICE_UNKNOWN`) among others. **This
  means item 22's "collection backend credential resolution failed -> shell
  prepares consent" symptom is not explained by a classification bug in this
  code** — by the time that debug line fires, the failure is already
  classified as `SecretStore`/`ERROR`, which this backend's own `authenticate_
  with` returns unchanged. If a consent window still opens after that, the
  mechanism has to be either EDS's own credential-resolution layer escalating
  independently of what this vfunc answers, or a different call in the same
  incident (e.g. the calendar factory's own `access_token` call, which
  classifies identically) — reinforcing, not replacing, item 22's own "Do"
  steps (1)/(2), which is exactly the EDS-source/multi-process reasoning
  sessions 4/5 already flagged as escalation-worthy. Nothing here narrows
  that further; recorded so a future session does not re-derive it.
* **`ConnectError::auth_result`/`client_error_code`, `LoginError::auth_result`,
  `reclassify_oauth2_rejection` (both the `connect.rs` and
  `jmap-backend-collection::authenticate` copies), and `finish_connect`/
  `finish_fan_out`.** All read against their own tests
  (`only_a_401_makes_evolution_ask_for_the_password_again`,
  `finish_fan_out_reclassifies_only_when_the_login_was_oauth2`, and
  siblings) and found to match: exactly one failure shape (`Client` with
  HTTP 401) ever produces `REJECTED`; `SecretStore` and every configuration
  error (`CredentialsRequired`, `NoSuchCollection`, `NoDefaultCollection`,
  `Account(SourceError)`) is `ERROR`; the OAuth 2.0 401-reclassification is
  applied only when the attempt that got the 401 was itself an OAuth 2.0
  bearer attempt, in both the book/cal and collection-backend copies. No
  asymmetry found between the two copies of the reclassification rule.
* **A real cross-crate asymmetry found, and fixed as F19 (below):**
  `jmap-mail`'s own OAuth2 token fetch (`jmap-mail/src/oauth2.rs::
  access_token`, used for the Camel mail store/transport) does **not** reuse
  `jmap_backend_core::oauth2::classify_failure` at all — it is a separate,
  independent implementation that read the `GError`'s message and freed it,
  with no call to `tracing` anywhere. This is not a soundness bug (Camel's
  `CamelAuthenticationResult` has no `REQUIRED` value to get wrong, and
  `StoreError::OAuth2` already maps to `CAMEL_AUTHENTICATION_ERROR`, the same
  conservative choice the EDS side makes — see that variant's own doc
  comment), but it is a real observability gap: item 20's "make every
  consent escalation traceable" pass instrumented the EDS-side
  `e_source_get_oauth2_access_token_sync` call with `reason`/
  `escalates_to_consent`/`error_domain`/`error_code` fields and never reached
  this one, so an item-22-shaped failure on the mail/Camel side (the same
  dead-D-Bus-peer error, reached through Camel's
  `camel_session_get_oauth2_access_token_sync` instead) was invisible in the
  journal from this call site even though the EDS-side one already names it.

### F19 — `jmap-mail`'s OAuth2 token fetch was untraced

**Fixed.** `jmap-mail/src/oauth2.rs::access_token`'s failure branch now calls
a new `trace_failure(error)` helper that reuses
`jmap_backend_core::oauth2::classify_failure` (already `pub`, already
cross-crate-tested) and emits the same `tracing::debug!` shape the EDS-side
`access_token` does — `reason`, `escalates_to_consent`, `error_domain`,
`error_domain_name`, `error_code`, `error_message` — before returning the
same `StoreError::OAuth2(message)` this call site has always returned.
Purely additive: the returned message and the `StoreError` variant are
unchanged; only the trace is new. `trace_failure` is split out precisely so
it can be driven with a hand-built `GError` in a unit test, the same
technique `jmap-backend-core::oauth2`'s own tests use for `classify_failure`.

TDD: three new tests in `jmap-mail/src/oauth2.rs`'s `#[cfg(test)]` module,
using a duplicated `CapturingSubscriber` (this crate depends on `tracing`,
not `tracing-subscriber`, matching `jmap-mail::service`'s own precedent) —
`a_dead_dbus_peer_is_traced_as_a_secret_store_failure` (the item-22 shape,
`g_dbus_error_quark()`/`G_DBUS_ERROR_SERVICE_UNKNOWN`, asserting
`reason=secret_store_failure`/`escalates_to_consent=false` and that the
message is unchanged), `a_missing_consent_is_traced_as_escalating` (an
ordinary `G_IO_ERROR_NOT_SUPPORTED` case, `escalates_to_consent=true`), and
`a_null_error_traces_without_a_message` (`reason=null_error`, no panic on a
NULL `GError*`). All three exercise `trace_failure` directly, since
`access_token` itself needs a live `CamelSession`/`CamelService` this crate's
own test suite does not construct elsewhere either.
