## 3. New-code audit

### `jmap-backend-core/src/resolver_thread.rs`: single resolver thread becomes a small fixed pool (F31's fix)

Commit `df8e19f3`. Net unsafe-site change: zero (confirmed both by
`rust/unsafe-baseline.txt`'s unchanged `jmap-backend-core 392` and by `git
diff b89adc7a..HEAD -- '*.rs' | grep -c unsafe` on added versus removed
lines, 3 and 3). The single dedicated thread/`GMainContext` becomes
`POOL_SIZE = 4` identical workers, round-robin dispatched; every FFI call
shape is reused verbatim per worker rather than invented fresh:

- **`spawn_resolver_worker`.** Same `g_main_context_new` /
  `push_thread_default` / `g_main_loop_new` / `g_main_loop_run` sequence the
  pre-delta single thread used, now run once per worker. The
  `ready_tx.send(SendContext(context)).is_err()` early-return path (receiver
  dropped before the context arrives) cleanly unrefs the loop, pops the
  thread-default, and unrefs the context rather than leaking; in practice
  unreachable, since `spawn_resolver_worker` calls `ready_rx.recv()`
  immediately after spawning with no intervening early return on the caller
  side. CLEAN.
- **`SendContext`'s `unsafe impl Send`/`Sync`.** Same justification the
  pre-delta single-context version already carried and this audit's
  predecessor already accepted: the context is valid for the process
  lifetime (never freed while any worker's loop runs, which is forever) and
  `g_main_context_invoke_full` is documented thread-safe from any calling
  thread. `Sync` is now load-bearing in a way it was not before: multiple
  caller threads read `worker.context.0` concurrently through a shared
  `&'static ResolverPool`, one worker per concurrent account setup, where the
  single-thread predecessor only ever had one context for one call site to
  share. Still CLEAN: the field is a `Copy` raw pointer read without
  mutation, and the one documented thread-safe API it is ever passed to
  tolerates arbitrary concurrent callers by design.
- **`invoke_cb`/`drop_payload`, the `GSourceFunc`/`GDestroyNotify` pair.**
  Structurally identical to the predecessor's already-audited pair: `Job =
  Option<Box<dyn FnOnce() + Send>>` boxed and leaked via `Box::into_raw`,
  reclaimed exactly once by `drop_payload`'s matching `Box::from_raw` after
  GLib destroys the one-shot source (`invoke_cb` always returns `GFALSE`).
  One allocation, one matching deallocation, on every path: either
  `invoke_cb` takes and runs the job (leaving `None` for `drop_payload` to
  no-op over) or the job is still `Some` when `drop_payload` reclaims it
  (the cancelled-before-dispatch case the type's own doc comment names,
  which cannot actually occur here since no worker context is ever torn
  down while live, but the code handles it correctly regardless).
  `invoke_cb`'s body still runs through `crate::trampoline::guard` before
  touching the job, so a panic inside a dispatched lookup cannot unwind
  across the `extern "C"` boundary on whichever worker thread it lands on.
  CLEAN.
- **`ResolverPool::next_worker`'s `Relaxed` `fetch_add`.** New in this
  delta: round-robin selection needs only distinct, advancing indices to
  spread load, not an ordering guarantee with the job the chosen worker goes
  on to run (that ordering is established by the `mpsc` channel each job
  uses to report its own result, not by the counter). `Relaxed` is the
  correct, minimal ordering for this use. CLEAN.
- **`resolve_srv`'s `rx.recv_timeout(RESOLVER_TIMEOUT)`.** Unchanged in
  shape from the predecessor: on timeout or disconnect (the dispatched job
  panicked before sending, caught by the trampoline guard, or the process is
  shutting down) the caller gets `None`, read as "no SRV record", not a
  panic. The queued job, if still pending, completes or is dropped
  independently on its own worker without affecting the caller. CLEAN.
- **`lookup_first_service_target`/`read_target`.** Byte-for-byte unchanged
  from the pre-delta version (ownership of the `GResolver` reference and the
  `GSrvTarget` list, read-before-free ordering); re-read anyway since the
  surrounding file changed around them. CLEAN.

**F31 is fixed, not merely mitigated.** The new
`a_slow_job_on_one_worker_does_not_delay_a_job_on_another` test proves the
actual property the finding named (a slow job dispatched to one worker must
not delay a job dispatched to a different one) with plain closures and
sleeps, deterministically, rather than relying on real DNS timing;
`round_robin_dispatch_reaches_every_worker` confirms dispatch actually
spreads across the whole pool rather than degenerating to one worker. Both
read correctly: the slow-path test asserts the fast job's completion
timestamp is under half the slow job's sleep duration, which only holds if
the two jobs genuinely ran on independent workers rather than one queued
behind the other. The residual version of F31's own concern (a pool of 4 can
still have a 5th concurrent account's lookup queue behind one of the 4 if
all are simultaneously slow) is the documented, intentional trade-off the
module's own doc comment states up front ("this many accounts can be
mid-setup at once before a new one queues, rather than every account queues
behind one") and is not a regression against any stronger guarantee this
project ever made; not re-opened as a new finding.

### `jmap-proto`/`jmap-client`/`jmap-mock`: `SieveScript/validate` matches RFC 9661's real wire shape

Commit `a75d29a3`. Pure protocol/data-shape correctness: `jmap-proto`'s
`SieveScriptValidateRequest` drops the invented `id`/`content` shortcuts for
the RFC's actual single `blobId` field, and `SieveScriptValidateResponse`
drops the invented mandatory `isValid` field for the RFC's actual
`error: SetError | null`, with `is_valid()` as a derived accessor rather than
a wire field. `jmap-client::Client::sieve_script_validate` now takes a
`blobId` directly; the new `sieve_script_validate_content` uploads first via
the already-audited `upload_blob` path, then validates the resulting blob,
matching the RFC's own required sequencing (§2.2 before §2.6). No `unsafe`
anywhere in any of the three crates touched (`jmap-proto`, `jmap-client`,
`jmap-mock` all stay at their existing baselines, `jmap-proto` and
`jmap-mock` at 0). CLEAN.
