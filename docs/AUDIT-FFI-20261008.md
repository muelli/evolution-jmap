## 3. New-code audit

### `jmap-config`: five new unsafe sites, all from item 91's OAuth2Dynamic unification

All five are additions, not edits of previously-audited code, and are listed
in `rust/unsafe-baseline.txt`'s bump. Reviewed against the hunt list:

- **`jmap-config/src/oauth2.rs::ensure_registered` (`#[cfg(eds_oauth2_dynamic)]`
  arm).** `unsafe { eds_sys::e_source_oauth2_client_get_type() }`: a
  zero-argument GType accessor, idempotent, self-registering on first call,
  the same shape every other `*_get_type()` call in this codebase already
  uses. CLEAN.
- **`jmap-config/src/oauth2.rs::read`.** The two `unsafe` blocks
  (`e_source_get_extension`, the `read_one` closure wrapping
  `get_string_property`) replace a prior single-class-cast version with a
  property-system call that works against either class behind
  `EXTENSION_NAME`. Contract: `source` valid (the function's own `# Safety`),
  extension non-null (checked via `e_source_has_extension` first, same
  pattern as before the diff). CLEAN.
- **`jmap-config/src/oauth2.rs::get_string_property` (new function).**
  `GValue` zero-initialised then `g_value_init`'d before use (the standard
  pairing `glib`'s own docs require — `g_value_init` on genuinely
  zeroed memory is defined, unlike on a previously-used `GValue`), filled via
  `g_object_get_property`, read through the existing `read_cstring` helper
  (which copies rather than borrows), and `g_value_unset` on every path
  including the early `None` from `read_cstring`. No leak, no
  use-after-unset: `text` is computed from the `GValue` before
  `g_value_unset` runs, not after. CLEAN.
- **`jmap-config/src/oauth2_service.rs::register` (new function).** The one
  `unsafe` call (`register_dynamic::<Service>(type_module)`) is reached only
  on the `else` branch of the `EDS_HAS_DYNAMIC_OAUTH2` check, i.e. only where
  this crate still owns the service; the `# Safety` contract (`type_module`
  is the one `e_module_load` was passed, alive for the call) is unchanged
  from what every call site already guaranteed before this function wrapped
  it. All three backend `module.rs` call sites were checked: each still
  passes its own `load`'s `type_module` straight through, none skip calling
  it inside the `g_once_init` guard those files already use. CLEAN.

### `jmap-mail/src/sasl.rs`: `eds_oauth2_dynamic` arms for `sasl_type`/`auth_type`

Two new `unsafe` blocks, cfg-gated, mirrored against the existing
`#[cfg(not(eds_oauth2_dynamic))]` arms they sit beside (not counted in the
`unsafe-baseline.txt` bump above since `jmap-mail`'s baseline entry is
separately tracked and did not need to move — grep confirms no baseline
change for this crate, meaning its total unsafe-site count stayed the same
across the cfg split, as expected for a mirrored arm rather than new
surface):

- **`sasl_type` (dynamic arm).** `eds_sys::camel_sasl_xoauth2_dynamic_get_type()`,
  same self-registering zero-argument shape as the oauth2.rs case above.
  CLEAN.
- **`auth_type` (dynamic arm).** `g_type_class_ref(sasl_type()).cast::<CamelSaslClass>()`
  then a field read (`.auth_type`). This is a transitive leading-field cast
  (`CamelSaslXOAuth2DynamicClass` -> ... -> `CamelSaslClass`), the same
  pattern `class_init` in the non-dynamic arm already relies on and that
  `eds-sys/tests/layout.rs` exists to catch a mismatch in; `CamelSaslClass`
  is upstream's own struct, not one bindgen free-hands, so the layout risk is
  the same as every other borrowed-vfunc-struct read elsewhere in this crate.
  The deliberate `g_type_class_ref` with no matching unref is justified
  in-line (the struct must outlive the provider, i.e. the process) — the
  same intentional-leak pattern the hunt list asks to see justified, and it
  is. CLEAN.

### `jmap-client`: EventSource reconnection, Last-Event-ID tracking, bounded timeouts

No `unsafe` anywhere in this delta's `jmap-client` changes
(`eventsource.rs`, `client.rs`, `transport.rs`) — pure safe Rust over
`std::net`/`std::sync`. Not this lane's feature turf, but the audit series
crosses lanes (same as F29/F30). Checked against the hunt list's
parser-robustness and concurrency items since this is new state shared
across threads:

- **SSE `id:` parsing** (`stream_events`). Handles `id: <value>` (sets),
  `id:` and bare `id` (both reset to `None`, matching the SSE spec's "empty
  id field resets the last event ID" rule), and leaves `last_event_id`
  unmodified on a frame with no `id:` line at all. A frame's id is latched
  only at the blank-line terminator, so a half-read frame cannot update it
  early. Verified by a new test
  (`stream_events_tracks_and_resets_event_id`).
- **`ConnectionContext` sharing** (`socket`, `last_id_slot`,
  `reconnect_count`, each its own `Arc<Mutex<_>>`/`Arc<AtomicU64>`). No lock
  is held across a blocking call: every `lock()` site here is a short
  get-or-set, and the socket mutex specifically is only ever locked to swap
  the `Option<TcpStream>`, never held during a read/write. No new deadlock
  shape versus the pre-delta single-`socket` mutex this replaces.
  `reconnect_count`'s `fetch_add` under `SeqCst` and the `Reconnected` item's
  `count` are read from the same `fetch_add` return value, so the notified
  count and the stored count cannot be observed to disagree.
- **Timeout plumbing** (`EventSourceTimeouts`, `ClientBuilder::connect_timeout`/
  `read_timeout`, `UreqTransport::with_timeouts`). Plain `Duration`
  configuration threaded through to `TcpStream::connect_timeout`/
  `set_read_timeout`/`set_write_timeout` and ureq's own per-phase timeout
  builder methods; no truncation (durations stay `Duration` throughout,
  never cast to a narrower integer type) and no unbounded-wait path
  reintroduced (every new blocking call site this delta touches now takes an
  explicit timeout where previously `TcpStream::connect` had none).

### `tests/functional/mail-live-client.c`: `TestSession::authenticate_sync` override

Test-harness-only, non-shipped C (item 90). `test_session_authenticate_sync`
calls `camel_service_authenticate_sync` once, and on
`CAMEL_AUTHENTICATION_REJECTED` clears the first error
(`g_clear_error`, correct: a stale `GError*` from the first attempt must not
leak into the second return), takes one password via
`test_session_get_password` (own signature matches exactly — `(session,
service, NULL, NULL, 0, &password_error)` against `(CamelSession *,
CamelService *, const gchar *prompt, const gchar *item, guint32 flags,
GError **error)`), and on no password propagates `password_error` into the
caller's `error` (via `g_propagate_error`, which assumes `*error` is `NULL`
at the call — true here, since `g_clear_error` ran immediately before).  On a
password, frees the local `gchar *` after `camel_service_set_password` (which
takes its own copy, per Camel's documented contract elsewhere in this
project), then retries. No leaked `GError`, no double-free, no use of a freed
password string. CLEAN.

already do and what this new test exercises), so this is expected behaviour
under the spec, not a gap.
