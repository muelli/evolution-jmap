### F11 — minor: a server-chosen year overflows the date arithmetic

**Where** `rust/crates/jmap-mail-sync/src/date.rs:62` (`epoch_seconds`), through
`days_from_civil` at `:190`, reached from
`rust/crates/jmap-mail-sync/src/message.rs:188` and `:189`
(`MessageSummary::from_email`).

**Why it is exploitable.** `epoch_seconds` splits the date, parses the year with
`i64::from_str`, and hands it to `days_from_civil` — which multiplies the year's
era by 146 097 and then multiplies the resulting day count by 86 400. Nineteen
digits parse. Twelve already overflow the second multiplication:
`days_from_civil(300_000_000_000, 1, 1)` is 109 572 749 280 472, and
`× 86_400` is 9.47 × 10¹⁸ against an `i64` ceiling of 9.22 × 10¹⁸.

The string is the server's, twice over: `receivedAt` on every `Email/get`
result, and `sentAt`, which is the sender's `Date` header relayed. Neither is
validated anywhere before this point — `jmap-proto` keeps `UtcDate` a string
deliberately, and this is the layer that interprets one.

The consequence differs by profile and neither is right:

* **Debug** — `attempt to multiply with overflow`, inside
  `MessageSummary::from_email`, inside a Camel refresh. `guard_bool` on
  `refresh_info_sync` catches it, so it is not an abort; it is a mailbox that
  fails to refresh for as long as the server keeps sending that message. One
  hostile `Email` hides a folder.
* **Release** — the profile in `rust/Cargo.toml` sets no `overflow-checks`, so
  the multiplication wraps and the summary row silently gets a date computed
  from nothing. Sorting by date, threading and the "recent" window all read it.

Observed before the fix, from the test below:

```text
thread 'a_year_no_calendar_can_hold_is_not_a_date_rather_than_an_overflow'
  panicked at crates/jmap-mail-sync/src/date.rs:62:10:
attempt to multiply with overflow
```

**Evidence** `rust/crates/jmap-mail-sync/tests/hostile.rs` —
`a_year_no_calendar_can_hold_is_not_a_date_rather_than_an_overflow` (three
years, one past `days × 86_400`, one past `era × 146_097`, one at
`i64::MAX`, all deserialised from `Email` JSON and run through
`MessageSummary::from_email`, which is the path a listing really takes),
`a_year_before_any_calendar_is_not_a_date_either` and, as the non-regression
half, `the_dates_a_real_server_sends_are_still_read`. Plus
`a_year_outside_the_four_digit_grammar_is_not_a_date` in `date.rs`'s own tests.
The first aborts the assertion as a *panic* without the fix, which is the point
of the finding.

**Fix** `9981e82`. The year is bounded before any arithmetic touches it, to
`YEARS = 1..=9_999` — RFC 3339 §5.6's four-digit `date-fullyear`, which RFC 8620
§1.4 makes a `UTCDate` and which `civil_from_days` already refused to write
outside of. One constant used by both directions, so the reader and the writer
cannot drift into disagreeing about which instants exist.

The behaviour change this brings is deliberate and small: `10000-01-01T…`
previously read as a valid instant and now reads as no date. It was never a
`UTCDate`, and `utc_date` would never have produced it.

### F13 — info: nothing checked that the mail provider's state is `Send + Sync`

**Where** `rust/crates/jmap-mail/src/store.rs:70` and `:80`,
`transport.rs:102`, `folder.rs:71` and `:84`, `summary.rs:144`,
`message_info.rs:116`, and the `unsafe impl` at `cache.rs:173-174`.

**Why it matters.** This is F7 in a third crate. `JmapStore` holds
`Slot<RwLock<Option<MailSync>>>` and `Slot<RwLock<Option<Listing>>>`; the
transport, the folder, the summary and the message-info row hold four more
`Slot`s between them. Every one of them is reached by turning the raw instance
pointer Camel dispatched on into a `&` by hand, so the compiler never sees the
sharing — and Camel drives a store from *more* threads than EDS drives a meta
backend from. An `Rc` or a `RefCell` appearing anywhere inside `jmap-client`,
`jmap-mail-sync` or the boxed `Transport` would be a data race in the mail
process rather than a build error.

`jmap-backend-book` and `jmap-backend-cal` each carry F7's assertion.
`jmap-mail` had none, and it is also the only crate outside `provider.rs` with a
hand-written `unsafe impl Send`/`Sync`: `MessageCache` wraps a
`*mut CamelDataCache` behind a `Mutex` and claims both. That is sound only while
the pointer never leaves the lock — a property of the module, not of the type —
and nothing would notice an accessor that started handing it out.

Checked by hand today: `MailSync`, `Client`, `Keywords`, `State`, `Id`,
`MessageCache` and all six `Slot`s are `Send + Sync`. **CLEAN**, and now pinned.

**Evidence** `rust/crates/jmap-mail/tests/hostile.rs` —
`everything_an_instance_holds_is_shareable_across_threads` and
`the_message_cache_still_claims_to_be_shareable`. A compile error rather than a
comment.

**Fix** `ae153b4`.

### F14 — info: server-chosen ids are substituted into a URL without encoding

**Where** `rust/crates/jmap-client/src/mail.rs:753` (`download_blob`), and the
same shape at `:738` (`upload_blob`).

**Why it is worth recording.** `download_blob` builds the request URL by
`str::replace` on the session document's `downloadUrl` template, substituting
`{accountId}`, `{blobId}` and `{name}` verbatim. RFC 8620 §6.2 requires the
client to URI-encode each variable's value. Nothing here does, and nothing
validates the values either: `jmap_proto::Id` (`id.rs:14`) is a newtype over
`String` with no grammar check at all, and both substituted values come off the
wire — the `blobId` from `Email/get`, and the `{name}` from
`jmap-mail-sync/src/lib.rs:412`, which passes the message uid.

A `blobId` carrying `#` truncates the URL at a fragment; one carrying `?` opens
a query string; one carrying `../` walks up the path. So a server can make this
client fetch a URL other than the one the template describes.

**Why it is info and not a finding with teeth.** The template is the *server's
own* `downloadUrl`, in the server's own origin, and a server that wants this
client to fetch a different URL can simply publish a different template. There
is no privilege to gain. What is left is a robustness and conformance gap: an
id the RFC does allow but that needs encoding produces a silently wrong request
rather than an error, and the code's comment at `lib.rs:405-408` justifies
itself by what "RFC 8620 §1.2 limits an id to" — which is an obligation on the
server, and the one thing the threat model says not to assume.

The asymmetry is the argument. `jmap-mail/src/cache.rs:466` (`valid_key`) already
implements exactly the §1.2 grammar, and applies it before a uid becomes a file
name, with a comment explaining that believing the server there would let it
choose where this provider writes. The same string is trusted at the URL
boundary.

**Recommendation** percent-encode each substituted value, or — cheaper and
narrower — reuse `valid_key`'s grammar as a constructor-level check on
`jmap_proto::Id`, so that an id which cannot be a file name also cannot be a
URL path segment. Not applied: it is a change to a shared type with 40-odd
construction sites and no live defect behind it, which is a refactor rather
than a fix.

### F15 — info: every response is capped at 10 MiB by a limit nobody here chose

**Where** `rust/crates/jmap-client/src/transport.rs:203-206`
(`UreqTransport::execute`).

**Why it is worth recording.** The body of every response — API call, session
document and blob download alike — is read with `ureq`'s `Body::read_to_vec()`.
That convenience method is documented as, and implemented as,
`with_config().limit(MAX_BODY_SIZE).read_to_vec()`, with
`MAX_BODY_SIZE = 10 * 1024 * 1024` (ureq 3.3.0, `src/body/mod.rs:30` and `:329`).

So this provider cannot download a message larger than 10 MiB — one photo
attachment — and cannot read an `Email/get` batch or a `Mailbox/get` whose JSON
exceeds it. The crate goes to real trouble over the limits that are *in the
protocol* (`maxSizeUpload` in `upload_blob`, `maxSizeRequest` in `api_call`,
`maxCallsInRequest` in `takes_calls_in_one_request`, all with their own tests)
and inherits this one silently from a dependency's default.

**It fails closed, which is why this is info and not a bug with a CVE shape.**
`ureq`'s limit reader returns `Error::BodyExceedsLimit` rather than a short
read (`src/body/limit.rs:24`), so the download is an error, not a truncated
message — and `jmap-mail/src/cache.rs` would refuse to cache a short entry
anyway. Nothing is corrupted; mail is simply unreadable above the cap.

**Recommendation** set the limit explicitly, from the account rather than from
the crate default: the natural ceiling for a blob download is the row's own
`size` plus slack, and for an API call the session's `maxSizeRequest`. Whatever
number is picked, it should be this repository's and have a test, because the
current one is invisible. Not applied: choosing it is a product decision about
how large a message an account will open, and the audit's mandate is to fix
clear-cut bugs.

**Coverage is complete: no unwind can reach C.** Re-confirmed that nothing sets
`panic = "abort"` anywhere in `rust/Cargo.toml`, the crate manifests, `cmake/`
or the workflows, so `catch_unwind` genuinely catches. Other checks:

* `guard_row` and `guard_summary` are the right shape: they refuse to run the
  body at all on an instance of another type, using
  `g_type_check_instance_is_a`, *before* the body reaches the instance struct.
  That check is what makes the bodies able to skip one of their own — and it is
  load-bearing rather than defensive, because a summary written before this
  provider's row type existed really does hand back a plain
  `CamelMessageInfoBase`.
* `parent_class()` in both `message_info.rs` and `summary.rs` peeks the
  **parent** type rather than the instance's own class, for the reason
  `finalize_trampoline` does: peeking its own would make a further subclass
  recurse into these same functions. Both are commented; both are right.
* `interface_init_trampoline` (new in `subclass.rs`) is guarded, and correctly:
  GObject calls it from inside `g_type_class_ref` while holding the type
  system's global lock, so an unwind there would be fatal. Its `GInterfaceInfo`
  is a per-iteration stack local, which is sound because both
  `g_type_add_interface_static` and `g_type_module_add_interface` copy the
  struct's fields rather than retaining the pointer.
* `InterfaceDecl::defaults` vs `filled_by` is a genuinely good design decision
  and the doc comment's reasoning is correct: `g_type_interface_peek` inside
  `class_init` happens to work on today's `gtype.c` by an ordering GLib does not
  promise, and `GInterfaceInfo.interface_init` is the documented contract.
* `Cancellation` (new in `cancel.rs`) declares `_scope` before `_bridge`, so the
  thread stops observing the flag before the handler feeding it is
  disconnected. Field order is load-bearing here and is documented as such.
* NULL handling in the new vfuncs: `can_refresh_folder` handles a NULL info,
  `get_message_sync` handles an empty uid, `JmapStore::borrow`/`JmapFolder::borrow`
  return `Option`, `read_envelope` handles NULL address arguments,
  `is_complete` handles a NULL collection, `resource_id_of` handles a NULL
  source, `commit` handles either source being NULL.

### 3.3 GObject memory and string ownership

Every reference-transferring call in the new code was checked against its
`transfer` annotation. The ones that would have been bugs:

* `camel_service_ref_settings` — `transfer full`; unreffed in `name_of` and in
  `attempt`, on both the success and the failure path (the `Result` is bound to
  a local *before* the unref, which is the ordering that matters). ✔
* `camel_service_ref_session` — `transfer full`; unreffed after
  `camel_session_authenticate_sync`. ✔
* `camel_network_settings_dup_*` — `transfer full`; every one goes through
  `take_string`, which frees. ✔
* `camel_folder_summary_get` — `transfer full`; unreffed in all four call sites
  (`message.rs:191`, `summary.rs:663`, `expunge.rs`, `synchronize.rs`). ✔
* `camel_folder_summary_get_array` / `_get_changed` — the caller owns the array
  and every string in it; freed with `camel_folder_summary_free_array` in all
  three walks, and each walk *copies* the uids out before doing anything that
  mutates the summary. That ordering is called out in the comments and is
  correct: `remove_absent` is the one walk that removes while iterating, and it
  does so over a snapshot that holds its own reference to each uid.
* `camel_message_info_dup_user_flags` — `transfer full`; freed with
  `camel_named_flags_free`. ✔
* `camel_message_info_take_user_flags` / `_take_references` — consume their
  argument, and are given a freshly built set / `GArray`. ✔
* `camel_address_format` — `transfer full`; `g_free`d after copying. ✔
* `e_collection_backend_new_child` — `transfer full`; unreffed in `fan_out.rs`
  on *every* path including the failures, with the comment saying so. ✔
* `e_collection_backend_ref_server` — `transfer full`; unreffed after
  `e_source_registry_server_add_source`. ✔
* `e_collection_backend_list_*_sources` / `claim_all_resources` — `transfer
  full` lists whose elements carry a reference each; `drain` frees with
  `g_list_free` (not `_full`) and passes the element references on, which is
  what both functions document. ✔
* `g_string_free(bdata, GFALSE)` in `summary_header_save` — hands over the
  `g_malloc`ed buffer, and the field's previous value is `g_free`d first, so a
  base class that started using `bdata` would not leak once per save. ✔
* `camel_util_bdata_get_string` — `transfer full`; `g_free`d each iteration. ✔
* `Unwritable` (new, `mime.rs`) owns its `GError` and frees it on drop, while
  `into_gerror` takes `self` by value and `ManuallyDrop`s it — so the error
  cannot be both handed over and freed. ✔
* `Changes` (new, `changes.rs`) owns the `CamelFolderChangeInfo` and frees it on
  drop; `as_ptr` hands out a borrow, which is right because
  `camel_folder_changed` does not take ownership. This is the type that makes an
  early return between allocation and emission not a leak. ✔
* `MessageCache` unrefs the `CamelDataCache` in `Drop`, and every `GIOStream` it
  opens is closed and unreffed on both the success and the failure path; the

  `g_set_error` over an already-set out-parameter cannot happen. ✔

Also checked: `FolderInfoChain::into_raw` still forgets `self`, so `Drop` and
the hand-over cannot both run; `attach_summary` uses
`camel_folder_take_folder_summary`, which takes the reference rather than adding

in `instance_init` is `clear`ed in `finalize` (checked for all six of
`jmap-mail`'s), without which the set behind each row would leak once per
message the folder ever listed.

Log formatting: `log_critical` and `debug_print` both pass the message as an
argument to a `"%s"` format rather than as the format itself, which is the
right call for a string a server chose.

### 3.4 Threading

The `unsafe impl Send`/`Sync` in production code, now three pairs:

* `jmap-mail/src/provider.rs:80-81`, `Registered(*mut CamelProvider)` —
  unchanged from session 1 and still justified: written once under a `OnceLock`,
  never mutated (pinned again by F12's byte comparison), never freed. ✔
* `jmap-mail/src/cache.rs:173-174`, `MessageCache` — **new**. The pointer is
  created in `open_bounded`, released in `Drop`, and reached only through the
  `Mutex`; no accessor hands it out. Sound as written, and F13 pins the claim.
  The lock is deliberately not held across a network fetch, which is the part
  worth overlapping. ✔
* The `Loaded` pairs in the three `tests/factory.rs` are test scaffolding.

The new thread-local cancellation (`CancelScope` in
`jmap-client/src/transport.rs`) is sound: it carries
`PhantomData<*const ()>` so it is `!Send` and therefore cannot be dropped on a
thread other than the one that installed it, it restores the previous
observation rather than clearing it (so nesting works), and
`Client::cancel_for_request` prefers the scope over the client-wide flag — which
is the right order, because a client-wide flag can only be set once and would
otherwise poison every later operation on the account. `observe(NULL)` installs
nothing, which is the honest reading of GIO's "this call cannot be cancelled"
and avoids hiding an outer cancellation. ✔

Lock discipline in the new code: every `Mutex`/`RwLock` recovers from poisoning
with `PoisonError::into_inner` rather than propagating, which is right for
state a panic elsewhere cannot corrupt. `apply_listing`/`apply_delta` hold
Camel's own summary lock across the whole reconciliation, so a reader never
sees half a mailbox. `set_summary_state` releases the lock before calling
`camel_folder_summary_touch`, which is the ordering that avoids taking two locks
in one order here and the other order elsewhere. ✔

### 3.5 Integer conversions

* `MessageSummary::from_email` — `u32::try_from(email.size).unwrap_or(u32::MAX)`,
  saturating, for a `size` the server chooses. ✔
* `summary_rows` — `usize::try_from(guint).unwrap_or(usize::MAX)`. ✔
* `parse` in `message.rs` — `gssize::try_from(source.len()).unwrap_or(gssize::MAX)`,
  with the reasoning written down: a negative length is read by Camel as "to the
  end of the buffer" and would walk off it. This is the best-reasoned cast in the
  crate. ✔
* `MessageCache::open_bounded` — `time_t::try_from(secs).unwrap_or(time_t::MAX)`,
  because Camel spells "no bound" as `-1` and a wrapped value would turn the

* `camel_address_length(...).max(0) as usize` in `envelope.rs`, then

* `folder_info::count`, `folder::saturate`, `settings::{set,get}_property` —

* `references_array` — `references.len() as u32` for `g_array_sized_new`'s

  Noted, not a defect.
* `message_id_digest` — `message_id.len() as isize` for `g_checksum_update`.

  ✔

### 3.6 TLS, plaintext-loopback, and credential-handling rules

* **TLS by default — three new readers, all correct.**
  `collection_source::server_of` (M6) and `account::read` (M7) each ask
  `e_source_has_extension(E_SOURCE_EXTENSION_SECURITY)` *before* any
  `e_source_get_extension`, and treat a missing `[Security]` group as secure.
  That is the subtle one session 1 identified — `ESourceSecurity:secure`
  defaults to FALSE — and both new call sites get it right and document why.
  `defaults::from_identity` opens a new account with `secure: true`. On the
  Camel side `ServerConfig::from_settings` reads
  `security_method != CAMEL_NETWORK_SECURITY_METHOD_NONE`, so every non-zero
  method is treated as secure, which is the safe direction. ✔
* **Plaintext to loopback only — still one function.** `source::origin` is
  called by the book backend, the calendar backend, the mail store, M6's
  `server_of` and M7's `complete::check`. There is no second copy of the rule
  anywhere in the new code (grepped). `is_loopback` is unchanged, and F12
  restored the four extra spellings that pin it failing closed. ✔
* **The setup UI refuses what the registry would refuse.** `complete::check`
  calls `origin` and keeps its error rather than restating the rule, and
  `tests/complete.rs` commits each case and reads it back with the *registry's
  own reader*. The one translation — an unfilled entry is `""` here and NULL in
  the keyfile — is a single line and is the tested one. This is the right
  design: a setup that happily wrote an account it knows will be refused would
  have told the user their password is safe to type into it. ✔
* **TLS propagates to the children.** `Child::settings` writes
  `[Security] Method = tls|none` from the account's own `secure`, and
  `a_plain_http_account_does_not_get_children_that_insist_on_tls` pins both
  directions. Each child then re-validates through `origin` at its own connect
  time, so a hand-edited child cannot be more permissive than the rule. ✔
* **Credentials only via `ESourceAuthentication`.** Re-checked across all the
  new code: the only two reads are
  `jmap_backend_core::marshal::password(credentials)` — the `ENamedParameters`
  EDS fills from libsecret — used by M6's `authenticate_with`, and
  `camel_service_get_password(service)` — what the `CamelSession` put on the
  service — used by M5's `attempt`. `ServerConfig` and `Account` have no
  password field; nothing reads one from a keyfile, a Camel settings object or
  an environment variable. M7 writes host, port, user, auth method and security
  method and no credential. ✔
* **Certificates.** M6's `authenticate_sync` deliberately leaves
  `out_certificate_pem` and `out_certificate_errors` alone, with the reasoning
  written out: TLS is `ureq`'s and the system trust store's, and a certificate
  this code cannot see is one it must not invite anyone to accept. The
  consequence — a self-signed server fails instead of offering a "trust this?"
  dialog — is the correct trade and is documented. ✔
* **`REJECTED` is still 401-only**, and M6 reaches
  `ConnectError::auth_result` rather than restating the rule. A panic in
  `authenticate_sync` becomes `ERROR`, not `REJECTED`, so a bug in this code
  cannot make Evolution throw away a correct password. ✔
* **The sending path.** `read_envelope` refuses rather than sends less: an
  address with no addr-spec, a `CamelAddress` that is not a
  `CamelInternetAddress`, an empty recipient list are each a refusal *before*
  the message is uploaded. A dropped recipient would be a message the user
  believes they sent; this cannot produce one. The identity lookup
  (`identity::best_match`) leans towards matching and says why — the server is
  the only side that can decide whether an address may be used, so being
  generous here costs a refused send and never mail leaving as somebody else.
  The wildcard is the single character `*` and never a prefix, and the domain
  match is whole-domain and never a suffix. ✔
* **Line endings on the wire.** `mime::crlf` inserts a CR before an LF that has
  none and touches nothing else — deliberately not the SMTP dot-stuffing, which
  would end up *inside* an imported message. A message stored with bare LFs
  would be one whose DKIM signature is computed over different bytes than the
  recipient verifies; this closes that. ✔

### 3.7 Hostile input beyond F11

* **A mailbox name is not a path.** `path::encode_component` percent-encodes
  `/`, `%` and NUL, and encodes `.` and `..` as whole components. A JMAP mailbox
  name may hold any character but NUL and is unique only among siblings, so this
  is the layer that stops a name inventing a hierarchy level or traversing the
  summary cache. The encoding is injective and the duplicate-name fallback
  appends `%23<id>`, which no encoded name can produce because `%` is escaped —
  so two mailboxes can never share a path, which would be a store handing back
  the wrong folder's mail. An empty name is refused outright at
  `FolderTree::from_mailboxes`. ✔
* **A uid is not a file name.** `cache::valid_key` implements RFC 8620 §1.2
  exactly — 1–255 characters of `A-Za-z0-9_-`, no leading dash — and a key that
  fails it is not cached rather than sanitised. `.` and `..` are refused by the
  character set; the empty string is refused explicitly. This is the check F14
  observes is *not* applied at the URL boundary. ✔
* **A truncated cache entry is not a message.** Both `load` and `store` compare
  the bytes against the size the row claims and refuse anything shorter, because
  MIME has no length and Camel's parser would happily make a message out of half
  a file. Shorter-only, deliberately: an exact comparison would make a slightly
  wrong server's mail permanently uncacheable. The reasoning is right and the
  asymmetry is the right way round. ✔
* **A NUL in a resource id is refused, not truncated.** `Live::new_child` uses
  `CString::new` rather than `cstring_lossy`, because truncating would silently
  ask EDS about a *different* resource and pair this collection's child with it.
  This is the one place in the codebase where the lossy conversion would have
  been wrong, and it is the one place that does not use it. ✔
* **The summary's stored format is versioned.** `summary_header_load` refuses a
  `bdata` whose leading number is not `HEADER_VERSION`, leaving the summary with
  no state rather than reading a future format's field as a state. The keyword
  column's `load` reads a count and then stops at the first name that is not
  there, so a truncated or foreign record costs the keywords and not the row.
  `camel_util_bdata_get_string` returns NULL once the cursor is exhausted, so
  the `map_while` terminates for any count. ✔
* **Protocol limits are asked before they are hit.** `api_call` refuses a
  request over `maxSizeRequest` without sending it; `upload_blob` refuses over
  `maxSizeUpload`; `takes_calls_in_one_request` checks `maxCallsInRequest`
  *before* a chain is built, because over the limit the server refuses the whole
  request and not just the call that went over. A server naming no limit is
  taken at its word rather than given an invented number. All three have their
  own test files. ✔
* **A delta is not a listing.** `apply_delta` and `apply_listing` differ in
  exactly what silence means, and the module says why: handing a delta to
  `apply_listing` would have the first delta that found one new message empty
  the folder. Only the delta path may put a uid on `uid_recent`, which is what
  runs the user's incoming filters — a listing cannot tell a message that just
  arrived from one that was always there, so a listing that marked its "added"
  as recent would re-run every filter over the whole mailbox. This is a
  correctness argument with a security edge (filters can delete and forward),
  and it is reasoned out correctly. ✔
* **`without_queueing` / `clear_pending_write`** — a row written from a listing
  must not land on the folder's work list, or a refresh would queue the whole
  mailbox to be written straight back to the server it came from. The bit is
  *restored* rather than cleared, so a change the user made a moment before the
  refresh is not lost in silence. ✔
* **`jmap-ical` and `jmap-vcard` re-probed.** No change since session 1 (both
  crates are untouched by the diff apart from F1/F2/F4's fixes); §2.7 of
  `docs/AUDIT-FFI.md` stands.
