# EDS version matrix

`eds-sys` is generated by `bindgen` at build time from the EDS headers that
`pkg-config` finds. That makes the FFI layer consistent with one EDS, the
one installed where `cargo build` ran. `eds-sys/tests/layout.rs` catches a
layout drift on that version (see `docs/eds-versions.md`), but not a renamed
symbol, a changed signature or a different layout in another release. The
matrix turns such a drift on a newer EDS into a failing CI job instead of a
segfault on a user's machine.

## The two legs

- **Pinned 3.52**: the `build` job in `.github/workflows/ci.yml`.
  `ci/install-deps.sh` installs Ubuntu 24.04's EDS 3.52 headers, and
  `ctest --test-dir build` includes the `rust-test-eds` target
  (`cmake/Rust.cmake`), which runs `cargo test` for `eds-sys`, `evo-sys` and
  every crate that needs EDS headers. This is the version that the plugin
  ships against.
- **Newer EDS**: the `eds-version-matrix` job, run on `workflow_dispatch`
  or a pull request with the label `run-eds-version-matrix`. It runs
  `ci/eds-matrix.sh` (clippy with `-D warnings`, then `cargo test` for the
  same crate set) in a digest-pinned Fedora container with
  `evolution-data-server-devel` and `evolution-devel`. Run
  `pkg-config --modversion camel-1.2` in the container to see which EDS the
  digest gives. The job has `continue-on-error: true`.

The container is pinned by digest, so moving to a newer EDS is an explicit
change to `ci.yml`.

## Reproducing the newer-EDS leg locally

Any machine with `docker` (or `podman`) can run the container that `ci.yml`
pins:

```sh
sudo docker run -d --name edsmatrix -v "$PWD:/src:ro" -w /work \
    fedora@sha256:6c75d5bf57cb0fa5aa4b92c6a83c86c791644496d9ac230de7711f5b8ec3b898 \
    sleep infinity
sudo docker exec edsmatrix dnf -y install git evolution-data-server-devel \
    evolution-devel pkgconf-pkg-config gcc clang-devel
sudo docker exec edsmatrix sh -c \
    'curl --proto "=https" --tlsv1.2 -sSf https://sh.rustup.rs | sh -s -- -y \
     --default-toolchain stable --profile minimal'
sudo docker exec edsmatrix sh -c \
    'cd /src/rust && PATH=/root/.cargo/bin:$PATH CARGO_TARGET_DIR=/work/target \
     ../ci/eds-matrix.sh'
```

The checkout is mounted read-only and cargo builds into `/work/target`, so
the host's `rust/target` is neither touched nor copied. Add
`--no-fail-fast` to the `cargo test` line in `ci/eds-matrix.sh` to see every
failure, not only the first.

## How a version difference is expressed

`eds-sys/build.rs` reads the bindings that bindgen generated and emits one
`cargo::rustc-cfg` for each entry of its `EDS_FEATURES` table whose marker
identifier is present. The test is "does the installed header declare this
identifier", never a version comparison, because a guessed version is
silently wrong on exactly the release it guessed wrong about.

- When both releases have the same operation with a different spelling,
  `eds-sys/src/compat.rs` has one wrapper and the rest of the tree calls it.
- When an API was removed with no replacement, the call site is
  `#[cfg]`-gated.
- A `rustc-cfg` reaches only the crate that emitted it. So `eds-sys` also
  publishes each detected feature as `cargo::metadata` (through its `links`
  key), and dependent build scripts such as `jmap-mail/build.rs` re-emit the
  cfgs that they need. Detection stays in `eds-sys/build.rs` only.

The current markers:

| cfg | Marker | Meaning |
| --- | --- | --- |
| `eds_vcard_version_enum` | `EVCardVersion` | vCard functions take an `EVCardVersion` (see (A0) below) |
| `camel_provider_url_helpers` | `CamelProviderAutoDetectFunc` | `CamelProvider` still has `auto_detect`, `url_hash`, `url_equal` |
| `camel_folder_search_object` | `camel_folder_search_new` | `CamelFolderSearch` exists and the provider implements search |
| `camel_summary_records` | `CamelMIRecord` | old summary record struct names |
| `camel_folder_get_uids` | `camel_folder_free_uids` | borrowed folder UID arrays |
| `eds_death_date_field` | `E_CONTACT_DEATHDATE` | the newer contact model (see (B)) |
| `camel_folder_search_body_sync` | `camel_folder_search_body_sync` | server-side body search entry point |
| `camel_uid_cache_get_new_uids` | `camel_uid_cache_get_new_uids` | the UID cache API |
| `camel_folder_thread_boxed` | `camel_folder_thread_messages_get_type` | the boxed thread type |
| `eds_credential_store_id` | `e_source_authentication_set_credential_store_id` | `credential-store-id` property (eds#663) |
| `eds_oauth2_dynamic` | `e_source_oauth2_client_get_type` | EDS's own OAuth2Dynamic support |
| `camel_data_cache_atomic` | `camel_data_cache_add_atomic` | atomic mail cache writes |

## Known differences between 3.52 and 3.60

### (A0) vCard and date strings, in `compat.rs`

- **`e_vcard_to_string` lost its format argument.** On 3.60 the version is
  given to `e_vcard_convert_to_string(EVCard *, EVCardVersion)`, and
  `EVCardFormat`/`EVC_FORMAT_VCARD_30` are replaced by `EVCardVersion` and
  `E_VCARD_VERSION_30`. Both legs call `compat::e_vcard_to_string_vcard_30`,
  which asks for vCard 3.0 explicitly: the one-argument call emits the card's
  own version, which `jmap-vcard`'s parser does not expect.
- **`e_contact_date_to_string` gained an `EVCardVersion` argument.** Wrapped
  as `compat::e_contact_date_to_string_vcard_30`.

### (A) The Camel surface of `jmap-mail`

- **`CamelFolderSearch` is gone (3.58+).** `camel/camel-folder-search.h` and
  the `camel_folder_search_util_*` helpers were removed in favour of
  `CamelStoreSearch`, and `CamelFolderClass.search_by_expression` and
  `.search_by_uids` were replaced by `search_sync`. The base class now
  installs a complete `search_sync` over `CamelStoreSearch`. So the provider
  implements the two old vfuncs on 3.52 and nothing on 3.58+, gated on
  `camel_folder_search_object`. `jmap-mail/tests/search.rs` checks search
  behaviour through whichever entry point the installed EDS has, including
  the complement and "all", so that a leg that ignores the expression
  fails.
- **Summary records were renamed.** 3.60's `CamelStoreDBMessageRecord` and
  `CamelStoreDBFolderRecord` (in `camel-store-db.h`) still have the `bdata`
  field that the provider uses. `compat::CamelSummaryMessageRecord` and
  `compat::CamelSummaryFolderRecord` alias them.
- **`CamelFolderSummaryClass.summary_header_save` changed shape** from
  returning a new record to filling a caller-owned
  `CamelStoreDBFolderRecord`. `jmap-mail/src/summary.rs` has both versions,
  `#[cfg]`-selected, sharing the function that writes `bdata`. Ownership of
  `bdata` (a `g_malloc`ed string freed by the record) is the same on both.
- **`camel_folder_summary_get_array`, `_free_array` and `_get_changed`**
  became `dup_uids` and `dup_changed`, freed with `g_ptr_array_unref`.
  Wrapped as `compat::summary_dup_uids`, `summary_dup_changed` and
  `summary_free_uids`. Calling the wrong one leaks instead of failing.
- **`CamelProvider` lost `auto_detect`, `url_hash` and `url_equal`.** The
  fields are `#[cfg]`-gated. The provider stays a struct literal that names
  every field, so a field that a future EDS adds is a compile error, not a
  silent NULL.
- **`camel_folder_get_uids`/`camel_folder_free_uids` became
  `camel_folder_dup_uids`**, a reference-counted array that the caller owns.
  Wrapped as `compat::folder_dup_uids` and `folder_free_uids`.
  `tests/functional/mail-client.c` has its own local wrappers with the same
  names.
- **`camel_folder_search_util_hash_message_id` became
  `camel_search_util_hash_message_id`** in `camel-search-utils.h`. Wrapped
  as `compat::search_hash_message_id`.

### (B) Contact model semantics

`eds-sys/tests/contacts.rs` characterises EDS's own C behaviour. These
results differ between the two legs, with the same function names and
signatures:

| vCard line | 3.52 resolves to | 3.60 resolves to |
| --- | --- | --- |
| `X-JABBER`, `X-AIM`, `X-GADUGADU`, `X-SKYPE`, `X-MATRIX`, `X-ICQ`, `X-MSN`, `X-YAHOO`, `X-GOOGLE-TALK`, `X-GROUPWISE` | the attribute-list field (for example `im_jabber`) | the first `_HOME_1` slot (for example `im_jabber_home_1`) |
| `ANNIVERSARY` | not mapped | `anniversary` |
| `X-EVOLUTION-ANNIVERSARY` | `anniversary` | not mapped |
| `DEATHDATE` | not mapped | `deathdate` (`E_CONTACT_DEATHDATE`) |
| `X-SIP`, `X-TWITTER`, `BDAY`, `X-DEATHDATE` | unchanged | unchanged |

Also, with no `FILE_AS`, `E_CONTACT_NAME_OR_ORG` is `"Family, Given"` on
3.52 and the full name on 3.60.

Only `E_CONTACT_DEATHDATE` is visible in the headers, so the tests use
`eds_death_date_field` as the switch for all of these. They change together
between the two releases that this repository tests.

Not decided: whether `jmap-vcard` should map differently on a newer EDS
(which IM field to read and write, `ANNIVERSARY` or
`X-EVOLUTION-ANNIVERSARY`, whether anything depends on `NAME_OR_ORG`).

### (C) clippy and bindgen's `_IO_FILE`

On the newer leg, rustc lints bindgen's accessor for the `_flags2` bitfield
of glibc's `_IO_FILE` (reached through the EDS headers) as
`unnecessary_transmutes`. `eds-sys/src/lib.rs` allows that lint on the
generated module, so `ci/eds-matrix.sh` can run clippy with `-D warnings`.

## The functional tests on a newer EDS

The functional tests (`docs/functional-tests.md`) can also run in the pinned
Fedora container, with the full `evolution` package installed. Two things to
know:

- Rootless podman drops `CAP_SETPCAP`, even with `--cap-add=SETPCAP`.
  `gnome-keyring-daemon` aborts without it, and so does every functional
  test. Run the container with `--privileged` (still confined by the rootless
  user namespace).
- The C clients in `tests/functional/` link no crate from this repository,
  so they use `EDS_CHECK_VERSION` for API differences.

## The `functional` job itself, reproduced from scratch

To reproduce the gated `functional` job of `ci.yml` exactly, use a bare
`ubuntu:24.04` container and run `ci/install-deps.sh`,
`ci/install-deps-functional.sh` and `ci/functional.sh`. The hosted runner
has a Rust toolchain preinstalled, so install one with `rustup` first.
`ci/install-deps.sh` installs `libclang-dev`, which bindgen needs.

Mount the checkout read-only (`-v "$PWD:/src:ro"`) and give cargo its own
target directory. Do not copy the checkout with `rust/target` into the
container; that directory is very large.

The `gui-smoke` job reproduces the same way, with
`ci/install-deps-gui-smoke.sh`, `cmake --install build --component
camel-provider` and `ci/gui-smoke.sh` (see `docs/gui-smoke-test.md`).

## Building EDS master locally

Some API changes are not in any packaged EDS yet. To test against EDS
master, build it in the pinned Fedora container:

```sh
sudo podman run -d --name edsmaster -v "$PWD:/src:ro" <the pinned fedora image> sleep infinity
sudo podman exec edsmaster mkdir -p /work
sudo podman exec edsmaster dnf -y install dnf-plugins-core git gperf cmake \
    ninja-build gcc gcc-c++ clang-devel pkgconf-pkg-config libdb-devel evolution-devel
sudo podman exec edsmaster dnf -y builddep evolution-data-server
sudo podman exec edsmaster sh -c \
    'cd /work && git clone --depth 1 --branch <branch> \
     https://gitlab.gnome.org/<fork>/evolution-data-server.git eds-src'
sudo podman exec edsmaster sh -c \
    'cmake -S /work/eds-src -B /work/build -G Ninja \
     -DCMAKE_BUILD_TYPE=RelWithDebInfo -DCMAKE_INSTALL_PREFIX=/work/prefix \
     -DENABLE_GOA=OFF -DENABLE_INTROSPECTION=OFF -DENABLE_VALA_BINDINGS=OFF \
     -DENABLE_GTK_DOC=OFF -DENABLE_GTK4=OFF -DWITH_KRB5=OFF -DWITH_OPENLDAP=OFF'
sudo podman exec edsmaster sh -c 'cd /work/build && ninja -j"$(nproc)" install'
sudo podman exec edsmaster sh -c \
    'curl --proto "=https" --tlsv1.2 -sSf https://sh.rustup.rs | sh -s -- -y \
     --default-toolchain stable --profile minimal'
sudo podman exec edsmaster sh -c \
    'export PATH=/root/.cargo/bin:$PATH
     export PKG_CONFIG_PATH=/work/prefix/lib/pkgconfig:/usr/lib64/pkgconfig:/usr/share/pkgconfig
     export LD_LIBRARY_PATH=/work/prefix/lib
     export CARGO_TARGET_DIR=/work/cargo-target
     cd /src/rust && cargo test -p jmap-mail -p jmap-config -p jmap-backend-collection --locked'
```

- Install `libdb-devel` before the first `cmake` configure. Otherwise CMake
  caches a failed `HAVE_LIBDB` check; delete `/work/build` and configure
  again.
- `evolution-shell-3.0` and the other `evolution-*` pkg-config files come
  from the packaged `evolution-devel`. `PKG_CONFIG_PATH` lists the
  from-source prefix first so that it wins for EDS.
- Build only the `install` target. A plain `ninja` also builds EDS's own
  test programs, which take much longer.
- The build needs several gigabytes. Delete `/work/eds-src` and
  `/work/build` after `ninja install`.

`cargo build -p eds-sys -vv` shows which `rustc-cfg` markers the build
script emitted.

## OAuth2Dynamic

EDS 3.63.1 and newer have their own OAuth 2.0 support for dynamically registered clients
(`EOAuth2ServiceDynamic`, the `"OAuth2 Client"` source extension). The
`eds_oauth2_dynamic` marker detects it. With it:

- `eds-sys`'s
  `upstreams_dynamic_oauth2_pieces_answer_to_the_names_this_project_spells`
  checks the two literals that bindgen cannot emit, `"OAuth2 Client"` and
  `"OAuth2Dynamic"`, against the running EDS.
- `jmap-config`'s
  `the_class_behind_the_group_is_the_one_this_eds_owns_it_with` and
  `what_this_crate_writes_is_what_upstreams_own_service_reads` check that
  the registration this project writes is the one that EDS's own service
  reads.
- `jmap-mail`'s SASL tests check that `camel_sasl_authtype("OAuth2Dynamic")`
  finds EDS's `CamelSaslXOAuth2Dynamic`.

EDS master also prefers the collection source in
`e_source_registry_server_get_access_token_sync`, gated on
`e_util_can_use_collection_as_credential_source`. This does not replace the
`follow_oauth2` binding in `jmap_backend_collection::child_added`: the gate
declines when a child's host and user are set and differ from the
collection's.

## What this does not catch

Struct-size and symbol checks are necessary, not sufficient. A contract
change with an unchanged signature and size (ownership, enum meaning, vfunc
assumptions) passes the matrix. Only behavioural tests (the functional
tests, on the shipped version) and reading the EDS release notes catch it.

## Supported versions

Build the plugin against the EDS that it will run with; that is the ABI
contract of every EDS module. 3.52 is the version that this repository
ships for. The newer-EDS leg shows what breaks next; it does not claim
support.
