### F27. The newer-EDS CI leg silently excludes the crate with the newest unsafe/FFI surface

**Medium (process). Fixed in this branch (one-line crate-list addition,
unverified against the container itself, see below).**
`ci/eds-matrix.sh`.

`jmap-ui` did not exist at the last audit. It does now: this delta adds its
EUIManager port, Evolution >= 3.55's replacement for `GtkUIManager` (`evo-sys`
gates it behind a compile-time `evolution_eui_manager` cfg, decided by
whether the installed headers actually have it). On this runner, and on the
`build` job's pinned Ubuntu 24.04 image, EDS is 3.52.3, so that cfg is false
and every `#[cfg(evolution_eui_manager)]` block in `jmap-ui` (most of
`snooze/action.rs`, `snooze/shell_ext.rs`, `snooze/browser_ext.rs`,
`send_later/extension.rs`) is not compiled at all here. The only leg of this
project's own CI that installs an EDS new enough to have EUIManager
(3.55+) is `eds-version-matrix`, which runs against a Fedora 44 container
resolving to EDS 3.60.2 (`docs/eds-version-matrix.md`).

That job runs `ci/eds-matrix.sh`, whose own header comment states its
contract in one line: "run the exact crate set `cmake/Rust.cmake`'s
`rust-test-eds` CTest target runs." That target (`cmake/Rust.cmake:88-93`)
lists `-p jmap-ui` at the end of its crate set. `ci/eds-matrix.sh`'s
`CRATES` array did not. So the one CI leg that could compile the
EUIManager port, and the only place `EUIActionEntry`'s field layout,
`e_ui_manager_add_actions_with_eui_data`'s signature, and every
`activate`/`change_state` callback arity in that port could be checked
against a real header, has never run over it. Not "not confirmed live",
which several open items in this project already carry honestly: literally
never compiled, by anything, anywhere in this project's own tooling.

**Why this is worse than a missing live-Evolution confirmation.** A GUI
feature this project cannot test in a headless VM still gets a real
`cargo build`/`cargo test` on every push, which at minimum proves the code
type-checks and its unit-level logic is correct. `jmap-ui`'s EUIManager
branch has had neither. Every struct literal in it (`EUIActionEntry`'s nine
fields, in order) and every `unsafe extern "C" fn` transmuted into a
`GCallback` (the `ActivateFn`/`MenuAction` pairs in `action.rs` and
`extension.rs`) is an assertion about a header this audit cannot read on
this machine either (evolution-shell-3.0 here reports 3.52.3, and no
`e-ui-*.h` exists anywhere on this runner), and that assertion has not been
checked by a compiler on any EDS release that would actually accept or
reject it.

**Compounding fact, not a separate finding.** `rust/unsafe-baseline.txt`'s
count for `jmap-ui` (327 as of this delta) is also measured only on 3.52,
so the project's one guard against unsafe surface growing silently
(`ci/checks.sh`'s unsafe-count meter, the subject of the last audit's F26)
has zero visibility into the EUIManager branch's unsafe sites either. The
newest and most intricate unsafe/FFI code in the tree is invisible to both
of this project's automated checks at once.

**Fix.** Added `-p jmap-ui` to `ci/eds-matrix.sh`'s `CRATES` array, making
the script actually match the contract its own comment already claimed.
`eds-version-matrix` runs `continue-on-error: true` and is gated to
`workflow_dispatch`/a PR label (`.github/workflows/ci.yml:139-155`), so this
change cannot turn a required check red; the next dispatch of that job is
what will, for the first time, tell someone whether `jmap-ui` actually
compiles against EDS 3.60.2.

**Not fixed by this branch, stated rather than hidden.** This session's
`claude` user is not in this runner's `docker` group (`getent group docker`
shows only the human operator, `muelli`), which is what let
`docs/eds-version-matrix.md`'s and `docs/NEWER-EVOLUTION-SPIKE.md`'s authors
reproduce the Fedora container locally and this one not. So the fix above
is unverified against the container it targets: it is possible `jmap-ui`
does not compile cleanly on 3.60.2 on the first attempt (a renamed symbol,
a struct-layout drift `evo-sys`'s allowlist has not been taught yet), in
which case the next `eds-version-matrix` dispatch will report exactly that,
which is the point of the job existing. Recommendation for whoever has
docker access next: dispatch `eds-version-matrix` once (or reproduce
locally per `docs/eds-version-matrix.md`'s recipe) to close this out for
real, the same way the 2026-08-17 measurement did for the other crates.

## 3. Audited and clean

### 3.1 `jmap-backend-collection`'s account-`"changed"` wiring and `allow_rename`

Already shipped 2026-09-18 (item 63 and its follow-up, `d67fb5cb`/`4bb75345`)
with its own tests; re-read here as part of this delta. `AccountWatch`'s two
atomics are correctly ordered (`populating()` before `claim_connection()` in
`populate`, so a repopulate the handler itself triggers cannot see a stale
"proven" bit from the populate that is currently running), the
`g_signal_connect_object` call's `gobject` parameter is `backend` (not
`source`), which is what ties the connection's lifetime to the backend
rather than requiring a stored handler id and a `dispose` override, and
`tests/source_changed.rs` proves both GLib facts the reasoning depends on
against the real linked library (`"changed"` takes no signal argument, and
a connection made against an object stops firing once that object is gone)
rather than assuming them. `allow_rename`'s `e_source_get_extension` call
cannot return NULL (it creates the extension if absent), so the unchecked
cast to `*mut ESourceCollection` is safe as commented.

### 3.2 `jmap-config`'s config-lookup error reporting

`config_lookup.rs`'s `run()` now reports a JMAP-shaped host's discovery
failure through its `error` out-parameter instead of staying silent, via
the new `oauth2_setup::Error::to_gerror`. That function's use of
`jmap_backend_core::error::set_raw_gerror` is the same helper F9's original
fix uses and still correctly refuses to overwrite an already-set `*dest`
(logging a critical and freeing the new error) rather than leaking or
double-freeing. Two tests (`cancellation_reads_back_as_g_io_error_cancelled`,
`every_other_failure_reads_back_as_g_io_error_failed_with_its_message`)
exercise both branches of the code-selection logic directly against a
freshly allocated `GError`, checked with `g_error_free` after each
assertion. No leak, no double free.

### 3.3 `jmap-mail`'s `CamelFolderClass::get_filename` and `CAMEL_PROVIDER_IS_EXTERNAL`

`camel_data_cache_get_filename` (`camel-data-cache.h`, present on this
runner) is confirmed a pure path computation with no `GError` parameter,
matching the module doc's claim; `MessageCache::filename` reads its
`gchar*` result once with `read_string` and frees it once with `g_free`,
no leak, no double free. The vfunc itself (`cache.rs`'s `get_filename`)
follows the same `guard_ptr`/`fail` pattern as this crate's other
error-reporting vfuncs, and refuses a hostile or absent uid the same way
`store`/`load` already do (`tests/cache.rs`'s
`a_uid_that_is_a_path_gets_no_filename` covers path-traversal-shaped uids
explicitly). `CAMEL_PROVIDER_IS_EXTERNAL` is a flag addition with no unsafe
surface of its own; `tests/provider.rs` asserts it is set alongside the
other flags this project's mail provider already carries.

### 3.4 `jmap-ui`'s vacation-page reentrant-borrow fix

Already shipped (`7e716fa3`, "fix a reentrant RefCell borrow on load"); the
pattern (read every widget pointer out of the `RefCell` under a short
immutable borrow, drop it, then call into GTK, which may reenter the same
`RefCell` through `"toggled"`) matches the reentrancy discipline the last
audit's 3.1 already found correct elsewhere in this crate
(`activate_custom`, `schedule_hold`, `snooze::action::finish`). No new
finding; recorded because this delta touches the same file's surrounding
lines.

### 3.5 `jmap-ui`'s EUIManager port, on the side this runner can actually check

The `#[cfg(not(evolution_eui_manager))]` half of every file this port
touches (`action.rs`, `shell_ext.rs`, `browser_ext.rs`, `extension.rs`)
compiles and passes its tests here unchanged in behavior from before the
port: the 3.52 code paths are the same functions, only renamed/moved behind
the new `#[cfg]`, and F25's fix (browser_ext's three-argument handler) is
untouched. The `#[cfg(evolution_eui_manager)]` half is exactly F27's
subject and is not covered by anything this audit could run; see F27 for
what is and is not being recommended about it.
