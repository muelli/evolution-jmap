## 3. New-code audit

### `jmap-backend-core/src/resolver_thread.rs` (new) + `resolver.rs` (rewritten): SRV lookups move to a dedicated resolver thread

Commit `1d166845`. Net unsafe-site change: old `main_context.rs` (2 sites) +
old `resolver.rs` (1 `unsafe fn` + 9 `unsafe {}` = 10) = 12; new
`resolver_thread.rs` (2 `unsafe extern`, 1 `unsafe fn`, 2 `unsafe impl`, 16
`unsafe {}` = 21) + new `resolver.rs` (0) = 21. Net +9, exactly matching the
`unsafe-baseline.txt` bump. Accounted for in full, not just claimed:

- **`spawn_resolver_thread`.** A process-lifetime thread pushes a fresh
  `GMainContext` as its own thread-default, builds a `GMainLoop` on it, and
  runs the loop forever. `ready_tx.send(SendContext(context))` hands the
  context pointer back to the spawning thread before entering
  `g_main_loop_run`; if the receiver already dropped (spawn canceled by a
  shutdown race that cannot actually happen here, since `RESOLVER_THREAD` is
  a process-lifetime `OnceLock` nothing ever drops), the thread unwinds the
  loop/context cleanly instead of leaking. Every `unsafe` block here is
  matched: `g_main_context_new`/`push_thread_default`/`g_main_loop_new` on
  entry, `g_main_loop_unref`/`pop_thread_default`/`g_main_context_unref` on
  both the early-return and the (unreachable in practice, since the loop never
  quits) fall-through path. CLEAN.
- **`SendContext`'s `unsafe impl Send`/`Sync`.** Justified in-line: the
  context is valid for the process lifetime (leaked by design, like the
  `CamelSaslClass` `g_type_class_ref` pattern F-series audits have already
  accepted elsewhere) and `g_main_context_invoke_full` is documented
  thread-safe to call from any thread. CLEAN.
- **`invoke_cb`/`drop_payload`, the `GSourceFunc`/`GDestroyNotify` pair.**
  `Payload = Option<ResolveRequest>` is boxed, leaked via `Box::into_raw`,
  and the raw pointer handed to `g_main_context_invoke_full` as `data`.
  `invoke_cb` always returns `GFALSE`, so GLib treats the dispatch as
  one-shot and calls `drop_payload` exactly once afterward, which reclaims
  the box with a matching `Box::from_raw` — one allocation, one matching
  deallocation, on every path (there is no path where the source is
  destroyed without ever dispatching: the context is never torn down while
  live). `invoke_cb`'s own body is wrapped in `crate::trampoline::guard`
  before touching the request, so a panic inside the lookup cannot unwind
  across the `extern "C"` boundary — the same trampoline-panic discipline
  prior audits required elsewhere in this codebase. CLEAN.
- **`resolve_srv`'s `rx.recv_timeout(RESOLVER_TIMEOUT)`.** If the dedicated
  thread never answers in time, the caller gives up and returns `None`
  (read as "no SRV record", the same fail-safe direction the module doc
  already establishes); the queued `invoke_cb` still runs eventually and
  tries `req.tx.send(target)` against a sender whose receiver is gone,
  which is a silently ignored `Err`, not a panic or a leak. CLEAN.
- **`lookup_first_service_target`/`read_target`.** Byte-for-byte the same
  function bodies the pre-delta `resolver.rs` had (ownership of the
  `GResolver` reference and the `GSrvTarget` list, read-before-free
  ordering), just relocated; no behavioural change, re-read anyway since the
  surrounding file moved. CLEAN.

**F31 (INFO, design concern, not fixed): the resolver thread is a single
process-wide serialization point for SRV lookups.** The pre-delta design ran
each lookup synchronously *on its own caller's thread*, with a private
context scoped to that one call (`PrivateContext::push()`), so two SRV
lookups from two different EDS backend worker threads already ran in genuine
parallel. The new design funnels every lookup, from every account, through
one dedicated thread's single `GMainContext`; `g_resolver_lookup_service` is
a blocking call, so while the resolver thread is inside one lookup, every
other queued `g_main_context_invoke_full` dispatch — i.e. every other
account's SRV lookup anywhere in the process — waits behind it. A slow or
hung resolution for one domain (a misbehaving system resolver, or a
`_jmap._tcp` zone an attacker-influenced domain owner points at a
black-holed nameserver — SRV targets are the kind of domain-owner-controlled
data this project's own `jmap-client` seam already treats as adversarial
input, see `resolver.rs`'s own module doc) therefore delays unrelated
accounts' lookups too, for up to GLib's own internal resolver timeout
(~60 s) per queued request ahead of them, not just the stuck one's own 75 s
cap. `tests/resolver.rs`'s `concurrent_lookups_from_several_threads_all_
answer_correctly` test, added by the same commit, confirms no deadlock and
correct answers under concurrent callers, but every lookup in it targets a
`.invalid` name that fails fast (RFC 6761), so it cannot and does not
exercise the slow-lookup-starves-everyone-else shape this finding describes.
This is a real behavioural regression versus the pre-delta design, but not a
memory-safety or credential-handling bug, and the trade-off it buys (fixing
glib#4041's unbounded per-call leak on a worker thread that never iterates
its own context, confirmed by this same file's own regression tests) is a
real one, not a mistake — a thread pool sized to the actual number of
concurrent accounts would keep both properties but is a larger redesign than
a re-audit should attempt un-asked. Documented per this audit's own
charter ("document design-level concerns rather than refactoring"), not
fixed here. Worth flagging for whoever next touches this seam; not turned
into feature work by this audit, since the charter scopes this stream to
auditing, not to opening new work on its own behalf.

### `jmap-client`: `contact_get`/`event_get` chunking, `ClientBuilder` paper cuts, `EventSource`/`TransportError` ergonomics

No `unsafe` anywhere (`jmap-client`'s baseline stays 0). Read for the hunt
list's integer-truncation and parser-robustness items since this is new
logic handling server-controlled limits and potentially large id lists:

- **`contact_get`/`event_get` chunking** (`contacts.rs`, `calendars.rs`).
  `max_objects = session.max_objects_in_get().and_then(|l|
  usize::try_from(l).ok()).filter(|&l| l > 0).unwrap_or(ids.len().max(1))`:
  a negative or zero server-advertised limit cannot produce a zero chunk
  size (the `filter` excludes zero, and a failed `try_from` or missing
  advertisement falls back to one whole-list chunk), so the loop's
  `take = rest.len().min(max_objects)` can never be zero while `rest` is
  non-empty, which rules out an infinite loop on a hostile or absent
  `maxObjectsInGet`. The empty-`ids` case (`rest` starts empty) still sends
  exactly one request, matching the doc comment's stated contract for
  state-only callers. Mirrors `email_get`'s pre-existing, already-audited
  shape. CLEAN, and covered by `jmap-client/tests/contact_get_chunking.rs`
  and `event_get_chunking.rs`.
- **`ClientBuilder::default()` now also reads `rebase_urls_from_env()`.**
  `rebase_urls_from_env()` and its use on every top-level `connect*`
  constructor both predate this delta (commit `64987c44`); this delta
  (`f96ac275`) only extends the same already-production-reachable env-var
  check to `ClientBuilder::default()` for consistency with callers that
  build through the default rather than a `connect*` convenience (e.g. the
  new `event_source` path). The env var is a plain boolean switch, not a
  source of a URL: the origin it rebases *to* is the one the client actually
  connected to, passed in by the caller, never read from the environment
  itself. No new attack surface versus what `connect*` already exposed.
  CLEAN.
- **`EventSourceSubscription`/`SharedHeaders`/`ClientBuilder`/`TransportError`
  `Debug`/`Display` impls.** Pure data formatting, no new locking pattern
  (the one new `.lock()` in `SharedHeaders::fmt` is the same mutex every
  other accessor already takes, released before the format call returns).
  CLEAN.

### `jmap-ical/src/event.rs`: `stated_duration` and `rrule_to_rule` fuzz fixes

Commit `4bb2e550`, already landed with its own red-first regression tests
(`jmap-ical/tests/fuzz_smoke.rs`:
`duration_with_leading_zeros_reaches_fixed_point_stability`,
`unmappable_rrule_frequency_reaches_fixed_point_stability`,
`zero_duration_trigger_with_custom_param_reaches_fixed_point_stability`)
before this audit started; re-read for correctness rather than re-discovered.
`stated_duration`'s digit normalization strips leading zeros per component
digit group (`"007D"` -> `"7D"`) and collapses an all-zero duration to the
canonical `PT0S`, matching JSCalendar/calcard's own canonical form; the
`rrule_to_rule` frequency gate now validates against the closed RFC
5545/8984 set (`rule.frequency` is already lower-cased at the one write site,
line 5017, before this check runs, so the match arms' lower-case spellings
are the only ones ever compared). Neither change touches `unsafe`/FFI
surface. CLEAN.

### `jmap-proto`: capability accessors gated behind their feature flags; `Task::links` loses its `contacts`-only type

Commit `7adb920f`. `Session::mail_capability`/`submission_capability`/
`contacts_capability`/`calendars_capability` and
`Account::submission_capability` are now `#[cfg(feature = "...")]`-gated to
match the modules they return types from, fixing a build that only broke
with some feature combinations `ci/checks.sh`'s default selection does not
exercise. `tasks::Task::links` changes from
`BTreeMap<String, crate::contacts::Link>` to `BTreeMap<String, Value>` so
the `tasks` feature does not require `contacts` to compile; this is a
wire-compatible relaxation (the field still (de)serializes the same JSON
shape, just without a typed accessor), not a parsing behaviour change. No
`unsafe`. CLEAN.
