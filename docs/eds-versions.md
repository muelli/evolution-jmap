# Which Evolution Data Server this builds against

An EDS backend module is not a program that talks to EDS over a wire. It is a
shared object EDS `dlopen`s into its own address space, whose classes derive
from EDS's classes, and whose instance structs begin with EDS's instance
structs. That means the module is bound to EDS by its **ABI** — struct
layouts, field offsets, vfunc slot order — and not merely by an API.

So the rule, which is the ordinary one for every EDS module and not something
this project invented:

> **Build the plugin against the exact Evolution Data Server it will be run
> on.** A `libebookbackendjmap.so` built against one EDS and installed beside
> another is undefined behaviour, not a compatibility question. Distribution
> packages get this right by rebuilding on every EDS update; anyone building
> from source has to do the same thing by hand.

## Supported versions

| EDS | Status |
| --- | --- |
| < 3.52 | **Not supported.** `build.rs` refuses to configure: the design rests on `EBookMetaBackend`/`ECalMetaBackend`, and older releases lack the `e_book_meta_backend_*` surface. |
| 3.52 | **The pinned target.** What the CI image installs, what `docs/functional-tests.md` drives, and the version every claim in this repository was measured against (Debian trixie / Fedora 40 era). |
| newer | **Expected to work, checked rather than assumed.** Nothing here is written to a 3.52-only API, but nothing here can promise a later release did not move a struct either. That is what the checks below are for. |

M7's configuration module carries an extra caveat of its own: Evolution 3.56
replaced GtkUIManager, so anything UI-XML-shaped has to be gated on the
Evolution version rather than the EDS one.

## How a version mismatch is caught rather than debugged

The bindings are generated by bindgen from the installed headers at build
time — deliberately, so that a struct that moved between releases is a *build*
input rather than a stale checked-in file describing an EDS nobody is running.
On top of that, `rust/crates/eds-sys/tests/layout.rs` asks the runtime what it
thinks, and there are three separate versions in play that can disagree:

1. what **pkg-config** resolved when `build.rs` chose the include paths —
   `eds_sys::EDS_HEADER_VERSION`;
2. what the **headers** say — `EDS_MAJOR_VERSION` and its two siblings,
   `#define`d in `libedataserver/eds-version.h` and carried into the bindings;
3. what the **library loaded at run time** says — `eds_major_version` and its
   siblings, `extern const guint` in `libedataserver`.

Each disagreement is a different fault, and each has a test:

- **(1) against (2)** — `pkg_config_describes_the_headers_it_pointed_at`. A
  `.pc` file that does not describe the headers beside it means `build.rs`
  chose its include paths off a version claim bindgen then did not read.
- **(2) against (3)** — `the_running_eds_can_serve_what_these_bindings_were_compiled_against`,
  which asks `eds_check_version()` rather than comparing numbers here: what
  counts as compatible is EDS's rule to state, not ours. This is the ABI
  contract above, as an assertion.
- **the layouts themselves** — every `assert_layout!` in that file, which
  cross-checks each subclassed struct's `size_of` against the size the running
  GObject type system registered with `g_type_query()`. This is the check that
  turns "the plugin writes into the wrong offset" from a runtime segfault into
  a red test.

Every one of those failures names the EDS it happened under — pkg-config,
headers and runtime, all three — because the point of running them across a
matrix of releases is to read a log afterwards and know which release broke.

`build.rs` also refuses outright, before generating anything, when the four
`.pc` files it probes (`libebackend-1.2`, `libedata-book-1.2`,
`libedata-cal-2.0`, `camel-1.2`) do not agree on a version. They ship in one
tarball, so a disagreement means a mixed installation — headers of two ABIs
behind one set of bindings, which has no correct answer to generate.

## What this does *not* catch

Nothing here notices **semantic** drift: a struct whose size and a function
whose signature stay identical while the contract underneath them changes —
who owns a returned pointer, what an enum value now means, what a vfunc is
allowed to assume when it is called. A size check is blind to all of it, by
construction.

Only two things catch that: the behavioural tests in
`docs/functional-tests.md`, which drive real EDS daemons and would notice a
changed contract as a changed outcome, and a human reading the EDS release
notes. The layout checks are necessary, not sufficient, and should not be read
as a claim that a green build on a new EDS is a working one.
