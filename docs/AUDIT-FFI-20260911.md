### F22. The Camel-sexp parser recurses once per `(`, without a cap

**Low, latent medium. Fixed in `cce0cd3`.**
`jmap-mail/src/search_sexp.rs`, `parse_value`/`parse_list`.

`search_sexp` is new since the last audit: it translates a Camel search
expression into an `Email/query` filter so a search can be answered by the
server instead of by the local summary. Its tokenizer is a pair of mutually
recursive functions — `parse_value` calls `parse_list` for a `(`, `parse_list`
calls `parse_value` for each element — with nothing bounding the recursion.
The nesting depth of the input is therefore the recursion depth of the parser.

**Why that is a defect and not a taste.** The module's own header states the
contract it breaks:

> The tokenizer here is not a general e-sexp parser … only to recognise the
> shapes Evolution actually generates and to **fail safely** (returning
> `None`, the same "stay local" answer as an untranslatable function) **on
> anything else, including malformed input**.

A stack overflow is not `None`. It is `SIGABRT`, and `search_by_expression`
runs on a Camel worker thread inside `evolution`, so the process that dies is
the one holding every account.

**Evidence.** A test calling `translate("(".repeat(100_000))` does not fail,
it takes the test binary down:

    thread 'deeply_nested_expression_is_refused_rather_than_overflowing_the_stack'
      has overflowed its stack
    fatal runtime error: stack overflow, aborting
    … (signal: 6, SIGABRT: process abort signal)

Bisected on the threshold: 2 000 parens survive, 5 000 do not, on a 2 MiB
Rust test thread. A GLib worker thread's default stack is the system's 8 MiB,
so the real threshold is roughly four times that — still trivially reachable
by anything that can write the expression.

**Why Low rather than High.** The expression is not server-controlled. It
comes from `mail/searchtypes.xml.in`'s rules, `message-list.c`'s `(match-all
…)` wrapper, and the user's own `filters.xml`/`vfolders.xml` — all local, and
all generating expressions four levels deep at most. A hostile *server* cannot
reach this; the string a user types in the search bar becomes a quoted
argument, not structure. It is a robustness bug against local malformed
input, which is exactly the class the module says it handles.

**Fix.** `MAX_DEPTH = 64`, threaded through both functions, refusing past it
with the same `None` every other unparseable expression gets. 64 is the number
`jmap-mail-sync`'s `folder` module already uses for a mailbox `parentId` chain
(F3's fix), and two orders of magnitude above anything Evolution generates.
Two tests: `a_run_of_open_parens_is_refused_rather_than_overflowing_the_stack`
(100 000 open parens, and a balanced 50 000-deep `(and …)`, both `None`) and
`nesting_up_to_the_limit_still_translates` (exactly `MAX_DEPTH` still
translates, one past it does not), so the cap is shown to refuse nothing real.

### F23. A server match set is narrowed by linear scan, quadratically

**Low (availability). Fixed in `220e25d`.**
`jmap-mail/src/folder.rs`, `server_matches`.

`search_by_uids` asks the server with `Email/query` and then keeps only the
uids Camel asked about. It did so with `[String]::contains` — one linear scan
of the restrict list per match, `O(matches × restrict)`.

**Why both lists are folder-sized.** `camel-vee-folder.c` hands
`camel_folder_search_by_uids` a whole subfolder's uid array on a vFolder
rebuild (`:474`) and again per subfolder on a changed-set pass (`:1121`). A
broad expression — "Unread Messages", "Hide Deleted Messages", any saved
search — matches most of the mailbox. So the two sizes are the account's
message count, twice.

**Evidence.** Measured on 50 000 × 50 000 Fastmail-shaped ids:

| | linear scan | `HashSet` |
|---|---|---|
| release | 5.71 s | 7.5 ms |
| debug | 21.6 s | 50 ms |

765× at 50 000, and it grows with the square: a 200 000-message mailbox is
about a minute and a half of a worker thread pegged while Evolution's message
list waits. That is a search that looks to the user like a hang.

**Fix.** A `HashSet<&str>` built once. Nothing about the answer changes — the
server's order is preserved and the membership test is the same — which the
first of the two new tests pins
(`narrowing_keeps_the_asked_for_uids_in_the_servers_order`). The second,
`narrowing_a_folder_sized_match_set_does_not_take_seconds`, is the red-first
one: against the unfixed tree it fails with

    narrowing 50 000 x 50 000 took 21.346693381s; the linear scan is back

and against the fix the pair runs in 0.09 s. Its 5 s deadline is two orders of
magnitude above what the fix measures, so it is a shape guard rather than a
benchmark.

### F24. F13's `Slot` guard had stopped naming every `Slot`

**Low (test coverage; a regression of a prior finding's fix). Fixed in
`c1bf08b`.**
`jmap-mail/tests/hostile.rs`.

F13's fix is one test asserting that everything `jmap-mail`'s instance structs
hold is `Send + Sync` — necessary because a vfunc receives a raw pointer and
makes a `&` by hand, so the compiler never sees the sharing. Its own doc calls
it "one test over all six fields", and that completeness is what makes it a
claim rather than a sample.

It had drifted to **five of the ten `Slot` types the crate declares**:

| `Slot<T>` | covered before | why it was missing |
|---|---|---|
| `Slot<RwLock<Option<Arc<MailSync>>>>` (store connection) | no | the list named the *transport's* `Slot<RwLock<Option<MailSync>>>`, a different type |
| `Slot<RwLock<Option<Listing>>>` (store folder listing) | no | never covered |
| `Slot<Mutex<Option<PushRefresh>>>` | no | never covered |
| `Slot<Mutex<Option<FolderRefresh>>>` | no | **new since the base commit** |
| `Slot<Mutex<Option<Id>>>` (row thread id) | no | **new since the base commit** |

**No soundness bug behind it.** Every missing type was checked one at a time
before the test was extended, and all are `Send + Sync`. The guard was right
about the code and wrong about its own coverage — which is the failure mode a
guard has, and the reason this is recorded rather than waved through. Extended
to all ten, with `Listing`'s two fields standing in for the struct (it is
private to the crate).

### F25. The browser snooze handler had the wrong arity for its signal

**Low (latent UB). Fixed in `999127c`.**
`jmap-ui/src/snooze/browser_ext.rs`.

`jmap-ui` connects to two signals both named `update-actions`, and they do not
have the same signature:

    e-shell-view.c:1090-1097   VOID__VOID, G_TYPE_NONE, 0
    e-mail-reader.c:5374-5382  VOID__UINT, G_TYPE_NONE, 1, G_TYPE_UINT

`snooze/shell_ext.rs` connects the two-argument shape to the first, correctly.
`snooze/browser_ext.rs` connected *the same two-argument shape* to the second.
Every `g_signal_connect_data` in this tree transmutes its handler through
`unsafe extern "C" fn()`, exactly as C does, so nothing but reading both
declarations could have caught it.

**Evidence, not argument.** `jmap-ui/tests/signals.rs` builds a signal shaped
exactly like the reader's on a plain `GObject` — no Evolution instance, no
display — and shows the marshaller calling a handler with three arguments:

    second arg = 0x2a        (the signal's own guint)
    third arg  = 0xdeadbeef  (the user data)

So the old handler's `_data: gpointer` was the `EMailReaderActionGroup`
bitmask, not its user data.

**Why Low.** Benign on the ABIs this ships on: the handler ignored that
argument, the user data it should have had is NULL, and a SysV or AAPCS callee
simply leaves the extra register alone. It is still a call through a function
pointer of the wrong type, and it is a trap set for whoever next needs user
data in that handler — they would get `0x2a`. Fixed by declaring the
parameter, with both upstream declarations cited in the doc comment.

### F26. The unsafe-count meter has been red on master since 2026-09-07

**Medium (process). Baseline fixed in `5920f04`; the process half is open.**

`ci/checks.sh` calls itself "the single definition of green", and its
unsafe-count meter exists for the one thing rustc and clippy cannot catch: a
crate's `unsafe` surface growing silently. It has been failing on master for
four days, and this audit found it by running the step rather than by reading
about it.

    c124fc8  2026-09-07  jmap-backend-core: fetch an OAuth 2.0 token on the credentials source
    jmap-backend-core: 368 -> 383 unsafe sites, unsafe-baseline.txt untouched

That is precisely the obligation the baseline file's own header states
("Growth stays possible, it just needs `unsafe-baseline.txt` updated in the
same commit"). Every `ci/checks.sh` run since would have exited 1 there.

**Why nobody saw it, which is the finding.** The last three audit reports each
record the same sentence: "`bash ci/checks.sh` stops at REUSE lint as always;
ran the rest by hand: `cargo fmt --check` … `clippy` … `cargo test`". "The
rest" has meant those three. The meter sits between clippy and tests and was
skipped every time — a by-hand reconstruction of a gate that omits one of its
steps is not the gate, and the step it omitted is the only one that is not
also enforced by the compiler. Two further notes on that premise:

* **The REUSE lint is not blocked on this runner.** `pipx run reuse lint`
  bootstraps and passes here (719/719 files, compliant with REUSE 3.3). The
  belief that `ci/checks.sh` cannot get past its first step is stale.
* **The meter itself works.** It caught the same drift at `d83acf9` and
  `c0e55a5` fixed it two commits later. It is the running of it that failed.

**Fixed here, in part.** `jmap-backend-core` raised 368 → 383 after reading
the 15 sites rather than rubber-stamping the number: they are the held
`ESourceCredentialsProvider` and its `ESourceRegistry`, the `unsafe impl
Send`/`Sync` on the holder, and the `credentials_source` walk — audited on
their own merits in §3. `jmap-config` lowered 220 → 217 in the same pass,
because the file says to regenerate and leaving the stale number lets three
sites reappear for free.

**Recommendation, not fixed by any commit.** Either run `bash ci/checks.sh`
whole — it does work here — or, if a step genuinely cannot run on a given
machine, name the skipped step in the report. "Ran the rest by hand" is what
let a red gate read as green for four days.

### 3.1 `jmap-ui`, the new UI-process surface (4 263 lines, 281 unsafe sites)

**Where its code runs.** `module-jmap-configuration.so` installs into
`EVOLUTION_MODULE_DIR` (`cmake/Packaging.cmake:183`), not
`EDS_REGISTRY_MODULE_DIR`, and `jmap_ui::module::load` is called from that
cdylib's `e_module_load` beside `jmap_config::module::load`. So the GTK type
registrations only ever happen inside `evolution`, never inside
`evolution-source-registry` — which is what keeps a GTK-less process from
being asked for `gtk_scrolled_window_get_type`.

**The widget subclass without a struct layout.** `VacationPage` is the first
GTK subclass in this workspace and is built so there is no layout to get
wrong: `type_sizes()` is `TypeSizes::of_parent(gtk_scrolled_window_get_type())`
— sizes from the running type system, after a `g_type_class_ref` because
`g_type_query` fills nothing for an unreferenced classed type — the subclass
adds no inline fields, and its state lives in one qdata box. `Instance =
GTypeInstance` and `Class = GObjectClass` are honest prefixes of any
GObject-derived struct, so the trampolines' casts stay in bounds.
`jmap-backend-core`'s own `queried_sizes_match_the_parent` pins that a type
registered on queried sizes is allocated at exactly them.

**The interface vtable it fills.** `EMailConfigPageInterface` is the one piece
of `EMailConfigPage` `evo-sys` generates — `BLOCKED_EVO_TYPES` spells
`_?EMailConfigPage` without a tail specifically to leave the interface
generatable while the instance stays an opaque handle. `evo-sys/tests/
layout.rs` holds the generated struct against the running library by reading
the *default* interface's own slots (`title` non-NULL, `sort_order == 0`,
`page_type <= 5`, `changed`/`setup_defaults`/`commit_changes` absent,
`check_complete`/`submit_sync`/`submit`/`submit_finish` present) — a field
read at the wrong offset could not produce that pattern. `PageInterface::
interface_init` writes into its own copy, pre-filled with the interface's
defaults, which is what leaves `check_complete` and `commit_changes` at
upstream's.

**The hand-written GTK constants.** `evo-sys/build.rs` emits seven enum values
as `raw_line`s because `Gtk.*` is blocklisted wholesale. Every one was checked
against the running GTK 3 by compiling a C program that prints them, not
against memory or docs: `GTK_ORIENTATION_VERTICAL=1`, `GTK_DIALOG_MODAL=1`,
`GTK_DIALOG_DESTROY_WITH_PARENT=2`, `GTK_MESSAGE_ERROR=3`,
`GTK_BUTTONS_CLOSE=2`, `GTK_RESPONSE_OK=-5`, `GTK_RESPONSE_CANCEL=-6`, and all
four enum types are 4 bytes, matching the `c_uint`/`c_int` they are declared
as. All correct.

**The worker/main-loop bridge.** `dispatch::spawn_for` is the one piece of
machinery every feature in the crate runs through, and it is right: the object
is held as a `GWeakRef` (`WeakBackend`), the answer is delivered through
`g_main_context_invoke_full` with a destroy notify that reclaims the boxed
closure exactly once whether it dispatched or the context was torn down, the
closure is `guard`ed, and `with_strong` holds a strong reference across
`finish` so a widget cannot be finalized mid-callback. A composer closed while
its session fetch is in flight is therefore unreachable rather than dangling,
which its own `a_dead_object_receives_nothing` test demonstrates by watching
the answer's `Drop` run without `finish` running.

**`RefCell` re-entrancy.** Three features keep per-widget state in a
`RefCell` in qdata, and all three run nested GTK main loops (`gtk_dialog_run`)
from within main-loop callbacks — the classic way to panic a `RefCell`. Every
borrow was traced: `activate_custom`, `schedule_hold` and `activate` take the
borrow inside a closure or block that ends before the dialog runs;
`snooze::action`'s `finish` explicitly `drop(snooze)`s before touching the
action and calls `update_sensitivity` after the `if let` block closes. No path
holds a borrow across a nested loop or across a re-entrant call.

**GObject ownership.** Actions are created, added to the group (which refs),
and the local reference released — `gtk_action_group_add_action` always
`g_object_ref`s (GTK 3), and the two action groups involved are per-editor and
per-window, so no second extension instance can replace an entry and strand
another's raw pointer. `e_source_lookup_password_sync`'s `gchar *` is copied
then `g_free`d, its `GError` freed; `gerror_message` frees what it reads;
`got_message` frees the composer's `GError` and unrefs the
`CamelMimeMessage` on every path, including the two early refusals.

**`unsafe impl Send`.** Four new ones, all the same shape — a `*mut ESource`
moved to a worker thread (`RefreshableSource`, and three `SendSource`s) — and
all justified by the same true fact: `ESource` refcounting is atomic and its
getters take the source's own property lock, which is the ground the EDS
backends already read sources on from worker threads. Each wrapper is moved
whole into the closure (the `let source = source;` line exists so edition-2021
per-field capture does not defeat the wrapper), the reference is taken before
the spawn and released inside the worker, and the pointer is only ever handed
to code that treats it as a live `ESource`.

**Arithmetic.** `schedule::resolve` computes a hold as `i64` seconds and
converts with `u64::try_from(...).ok().filter(|s| *s > 0)` — no cast, no
negative hold. `activate_custom` checks `chosen - now <= 0` before casting,
which also catches `e_date_edit_get_time`'s `-1` "no date set". Both preset
and custom paths re-check against the server's `maxDelayedSend` in
`schedule_hold`, so one place owns the rule.

**Injection.** The vacation page builds its patch with `serde_json::json!`,
never string concatenation, and refuses a malformed or backwards date before
the patch exists. `translate_with` is a pure-Rust single-pass substituter — no
`printf` — so a server string placed in a message cannot consume the next
argument, and the two message dialogs pass `"%s"` as the format with the text
as the argument.

### 3.2 The `Bcc` header on the JMAP send paths — checked, and correct

Worth recording in full because the analysis went the other way first.
Camel's SMTP transport removes the `Bcc` header immediately before writing the
message to the wire and restores it afterwards
(`camel-smtp-transport.c:1891-1893` and `:1958-1963`), and Evolution's own
send path does **not** do it for the transport (`e-mail-session-utils.c`'s
`mail_session_send_to_thread` strips and restores only `X-Evolution-*`). The
composer does put a real `Bcc:` header on the message it builds
(`e-msg-composer.c:603-605`). So this project's transport (`jmap-mail/src/
send.rs`) and `jmap-ui`'s scheduled send both upload a message that still
carries `Bcc:`, and neither strips it.

That is correct, and the reason is RFC 8621 §7.5:

> The server **MUST** remove any Bcc header field present on the message
> during delivery.

The obligation is the server's, and taking it on in the client would be
actively worse here: the uploaded `Email` *is* the Sent copy (moved
Drafts → Sent by `onSuccessUpdateEmail`), unlike SMTP where Evolution appends
a separate copy from the in-memory message, so stripping would delete the
user's own record of whom they blind-copied. The envelope is carried
explicitly in both paths rather than left for the server to derive from
headers, which is the half that would actually leak or drop a blind recipient,
and `jmap-mail/src/envelope.rs`'s module doc already reasons about exactly
that. No finding.

### 3.3 The new server-side search path

`search_by_expression`/`search_by_uids` are new, are `unsafe extern "C"` slots
Camel dispatches, and return a `GPtrArray` Camel frees. The allocation
discipline is right and it is not obvious: this class installs no `search_free`
of its own, so `folder_search_free` (`camel-folder.c:1070-1078`) frees each
element with `camel_pstring_free` — and `pstring_uid_array` accordingly
allocates every element with `camel_pstring_strdup`, not `g_strdup`. Verified
against that function's source. The fallback split is also right: a
disconnected store folds to the local summary search (the offline case), while
a server that *was* asked and failed is reported rather than masked by a
possibly-stale local answer.

### 3.4 The credentials-source resolution (`c124fc8`)

The 15 `unsafe` sites F26 is about. `access_token` now resolves a child source
to its collection before asking EDS for a token, because EDS 3.52 computes the
answer for the source as given and three children asking at once are three
refresh exchanges spending the same refresh token — which a rotating server
reads as replay. The walk is `e_source_credentials_provider_ref_credentials_
source`, which is what Evolution's own mail session uses. Three things were
checked and hold: the parent check comes **first**, so the collection backend
running inside `evolution-source-registry` never builds an `ESourceRegistry`
that is a D-Bus client of itself; the returned reference is transfer-full and
the `owned` flag beside it is what decides the `g_object_unref`, with the test
`a_parentless_source_is_its_own_credentials_source` asserting both halves
(pointer identity *and* `owned == false`, because a caller that unrefs what it
did not take drops the backend's own source); and the provider holds the
registry strongly, which it must, since `e_source_credentials_provider_new`
keeps only a `GWeakRef` to it.

### 3.5 The ROADMAP security rules, on the new surface

* **TLS by default, plaintext to loopback only.** `jmap-ui` does not have its
  own connect path: `link::connect_account` goes through
  `source::SourceConfig::from_source` and `source::connect`, so it inherits
  `connect_target`'s rule (`!secure && !is_loopback(host)` →
  `SourceError::InsecureTransport`) unchanged. The URL-rebasing opt-in it also
  inherits is per-account or per-process and predates this audit's base.
* **Credentials only via `ESourceAuthentication`.** `link::connect_account`
  reads `[Authentication] Method` off the source and branches three ways
  exactly as the backends do — OAuth 2.0 through
  `e_source_get_oauth2_access_token_sync`, an API token or a password through
  `e_source_lookup_password_sync`. Nothing in `jmap-ui` reads a credential
  from anywhere else, and it deliberately does *not* prompt (a settings page
  has no `ESourceCredentialsProvider`), reporting instead.
* **401 handling.** Every server call in the crate goes through
  `AccountLink::call`, which refreshes the access token and retries once —
  the same `retry::retry_once_after` the backends use — and only the OAuth 2.0
  path is refreshable, since for a stored password a 401 means the password is
  wrong and retrying would ask again with the same one.

### 3.6 Smaller new surfaces read and found clean

* **`jmap-backend-core::mime::write_message`** (moved here from `jmap-mail`,
  now shared by append, transport and scheduled send). Flushes before reading
  the buffer, copies rather than steals it, and the `GError` is owned by
  `Unwritable` with a `Drop`, so a caller that drops the failure frees it.
  `into_gerror` uses `ManuallyDrop` correctly to hand ownership on.
* **`PrivateContext`** (`main_context.rs`, glib#4041). `!Send`/`!Sync` via
  `NonNull`, so the pop cannot happen on the wrong thread; iterates before
  popping, which is the load-bearing step; used in exactly one place
  (`resolver.rs:107`), scoped to the SRV lookup, so no long-lived object
  attaches its sources to a context that is about to go away.
* **`subclass::parent_class<C>`**, the new shared chain-up peek. Replaces four
  hand-written `g_type_class_peek(...).cast::<C>().as_ref()` sites with one;
  every caller is a direct subclass of the type it names, which is what makes
  the peeked class the right parent.
* **`push::Work`** and the coalescing rewrite. The `again: bool` became a
  union of two flags, and `work_requested_during_a_pass_unions_into_the_next_
  one` pins the thing that could have been lost — a `Mailbox` push and an
  `Email` push arriving during one pass must both be answered by the coalesced
  one. `refresh_open_folders` now moves each array element into an `Owned`,
  which matches `camel_object_bag_list`'s no-element-free-function array.
* **`get_quota_info_sync`** and `CamelFolderQuotaInfo`. `camel_folder_quota_
  info_new` copies the name and zeroes `next`; the chain is built head/tail
  with no double-linking; an account with no Mail-scoped quota returns NULL
  *with* `G_IO_ERROR_NOT_SUPPORTED` set, which is `camel-imapx-folder.c`'s own
  answer and not a NULL-without-error (which would earn a GLib critical).
* **`message_info`'s fifth column.** `save`/`load` append and read a
  count-then-value pair after the keywords; a row written before the column
  existed reads `camel_util_bdata_get_number(cursor, 0)` past the end and gets
  the default `0`, i.e. "absent", so the format change is backward compatible.
* **`jmap-proto`'s new modules** (`blob`, `quota`, `sieve`, and the mail and
  calendar additions). No `unwrap`, `expect`, `panic!`, indexing or slicing
  anywhere in them — every field is `serde`-decoded and every optional stays
  optional. The crates are `#![forbid(unsafe_code)]` and metered at 0.
* **The scheduling iCalendar payload.** `scheduling_ical` is new and writes
  two values `event_to_ical` never does (`METHOD`, and a `RECURRENCE-ID` for
  an occurrence-scoped message), both supplied by the caller. F1/F2's class
  does not reappear through them: calcard escapes a CR or LF into the literal
  two-character sequence and the document's shape is unchanged. Now covered
  permanently — §4.
